### 1. Section Overview

#### What This Section Is About
This section covers data interchange between Pandas DataFrames and all major non-tabular/non-spreadsheet file formats and database systems. While CSV and Excel are row-oriented textual and spreadsheet containers, real-world data engineering pipelines interface with diverse protocols: semi-structured JSON payloads (standard JSON and JSON Lines/NDJSON), web-scraped HTML tables, relational SQL databases via SQLAlchemy connection pools, high-performance columnar binary Parquet storage backed by Apache Arrow, and Python-native binary Pickle archives. This section covers serialization, deserialization, schema normalization, memory efficiency, and query pushdown optimization across each format.

#### Why These Pandas Concepts Matter
1. **API Integration & Semi-Structured Data:** REST APIs, microservices, and NoSQL databases return nested JSON. A data engineer must flatten hierarchical JSON payloads into tabular DataFrames using `pd.json_normalize()` and stream multi-gigabyte log files using JSON Lines (`lines=True`).
2. **Database Interchange & ETL Workflows:** Relational databases (PostgreSQL, MySQL, Snowflake, SQLite) are the backbone of production applications. Moving data in and out of databases via `read_sql()`, `read_sql_query()`, `read_sql_table()`, and `to_sql()` with connection pooling and chunking is a mandatory daily responsibility.
3. **High-Performance Big Data with Parquet:** Modern data lakes (AWS S3, Google Cloud Storage, Databricks, Snowflake) store data almost exclusively in Apache Parquet. Parquet provides columnar compression, dictionary encoding, and predicate pushdown, allowing queries to load only requested columns and row groups while running 10x-50x faster than CSV.
4. **Fast Scratch Serialization with Pickle:** When preserving exact Python object types, hierarchical indices, or trained machine learning models during local prototyping, Pickle serialization saves and restores state without any schema translation loss.

#### Where They Are Used in Real Projects
- **Data Lake & Lakehouse Engineering:** Writing partitioned, Snappy-compressed Parquet files to cloud object storage for consumption by Spark, Trino, and Snowflake.
- **REST API ETL Pipelines:** Fetching multi-tiered JSON responses from payment gateways (Stripe, PayPal) and normalizing nested customer/transaction arrays into relational tables.
- **Financial & Regulatory Web Scraping:** Scraping balance sheets, stock tickers, and economic indicators from public tables using `pd.read_html()`.
- **Database Synchronization:** Ingesting transaction batches from operational OLTP databases into analytics staging environments using chunked `to_sql()` with `method='multi'`.

#### What a Fresher Should Be Able to Do
- Flatten deeply nested JSON responses into clean 2D tabular DataFrames using `pd.json_normalize()`.
- Stream multi-gigabyte JSON Lines (`.jsonl` / `.ndjson`) files using `pd.read_json(..., lines=True, chunksize=N)`.
- Connect Pandas to relational SQL databases via SQLAlchemy engines, executing parameter-bound SQL queries and writing DataFrames via `df.to_sql()`.
- Read and write Snappy-compressed Parquet files via `pd.read_parquet()` and `df.to_parquet()`, applying column pruning (`columns=[...]`) and predicate filtering (`filters=[...]`).
- Scrape HTML tables from web pages and HTML strings using `pd.read_html()`.
- Safely serialize and deserialize in-memory Python objects with `to_pickle()` and `read_pickle()`, while understanding security implications.

### 2. Topic-Wise Interview Concepts

#### 2.1 JSON Formats: `read_json()`, `to_json()`, and `pd.json_normalize()`
JSON (JavaScript Object Notation) is the standard data interchange format for web APIs. Pandas handles JSON through two distinct pathways:
1. **The `orient` Parameter in `read_json()` and `to_json()`:**
   - `'records'`: List of dictionary records `[{"col1": val1, "col2": val2}, ...]`. The most common API format.
   - `'split'`: Dictionary with separate keys for `index`, `columns`, and `data`. Compact and efficient.
   - `'index'`: Dictionary keyed by index labels `{row_id: {col1: val1, col2: val2}}`.
   - `'columns'`: Dictionary keyed by column names `{col1: {row1: val1, row2: val2}}`. Default for `to_json()`.
   - `'values'`: Raw 2D nested array of cell values `[[val1, val2], [val3, val4]]`.
2. **JSON Lines (`lines=True`):**
   - In standard JSON, the entire file must be valid JSON enclosed in `[...]` or `{...}`. Reading a 10 GB standard JSON file requires parsing the entire file into memory at once.
   - JSON Lines (NDJSON) writes each record as an independent valid JSON object on a single line separated by `\n`. This enables chunked out-of-core streaming:
     ```python
     for chunk in pd.read_json(
         "server_logs.jsonl", lines=True, chunksize=100_000
     ):
       process(chunk)
```
3. **Flattening Nested Payloads with `pd.json_normalize()`:**
   - Nested JSON cannot be unpacked cleanly with `read_json()`. `pd.json_normalize()` unrolls hierarchical dictionaries and lists:
     ```python
     payload = {
         "id": 101,
         "user": {"name": "Alice", "city": "NYC"},
         "orders": [
             {"item": "Laptop", "price": 1200},
             {"item": "Mouse", "price": 25},
         ],
     }
     # Normalizes nested 'orders' while pulling parent metadata
     df = pd.json_normalize(
         payload, record_path=["orders"], meta=["id", ["user", "name"]]
     )
```

#### 2.2 HTML Table Scraping: `pd.read_html()` and `to_html()`
Pandas can inspect raw HTML documents or fetch live web pages over HTTP, extracting all `<table>...</table>` elements into Python lists of DataFrames:
- **Underlying Engines:** Relies on `lxml`, `html5lib`, or Python's `BeautifulSoup4`.
- **Targeting Specific Tables:** Use the `match` parameter to specify a regex or substring contained in the target table's text:
  ```python
  # Scrapes only tables containing the string "Market Cap"
  tables = pd.read_html(
      "https://example.com/stocks", match="Market Cap", flavor="lxml"
  )
  target_df = tables[0]
```
- **Exporting to HTML:** `df.to_html("report.html", classes="table table-striped", index=False)` renders DataFrames into HTML strings styled for web dashboards.

#### 2.3 SQL Databases: SQLAlchemy, `read_sql()`, and `to_sql()`
Pandas interfaces with relational databases via SQLAlchemy 2.0+ `Engine` instances or raw DBAPI connections:
1. **Reading from SQL:**
   - `pd.read_sql_query(sql, con, params=...)`: Executes a SQL `SELECT` statement directly. Preferred for filtered aggregations.
   - `pd.read_sql_table(table_name, con)`: Reads an entire database table using SQLAlchemy metadata reflection.
   - `pd.read_sql(sql_or_table, con)`: Delegates to `read_sql_query` if given a query string, or `read_sql_table` if given a table name.
   - **Streaming SQL via `chunksize`:** Setting `chunksize=N` returns a generator yielding DataFrames of $N$ rows, keeping memory constant when extracting massive tables.
2. **Writing to SQL (`df.to_sql()`):**
   - `name`: Target database table name.
   - `con`: SQLAlchemy engine or connection.
   - `if_exists`: `'fail'` (raise ValueError if exists), `'replace'` (drop existing table and recreate), or `'append'` (insert new rows).
   - `index`: Set `index=False` unless the index is a primary key column.
   - `chunksize` & `method='multi'`: By default, Pandas executes individual `INSERT INTO ... VALUES (...)` statements row-by-row, which is slow. Setting `method='multi'` with `chunksize=1000` bundles rows into multi-value batch inserts (`INSERT INTO ... VALUES (...), (...), ...`), accelerating write throughput by 10x-50x.

#### 2.4 Columnar Storage: Apache Parquet (`read_parquet()` and `to_parquet()`)
Apache Parquet is an open-source, columnar binary storage format designed for high-performance analytical processing:
1. **Columnar vs Row-Oriented Storage:**
   - In row-oriented formats (CSV, JSON, SQL rows), adjacent bytes on disk represent consecutive fields of the same record. Reading 1 column requires streaming all columns through CPU cache.
   - In Parquet, values for each column are stored contiguously in memory and on disk, partitioned into row groups (typically 64 MB to 128 MB).
2. **Column Pruning (Zero-Cost Projections):**
   - Passing `columns=['colA', 'colB']` instructs the Parquet reader to read only the byte ranges on disk corresponding to those two columns, bypassing all other columns completely.
3. **Predicate Pushdown (Filter Pushdown):**
   - Parquet metadata stores min/max statistics for every column in each row group. When you pass `filters=[('timestamp', '>=', '2024-01-01')]`, the reader inspects row group metadata headers. If a row group's maximum timestamp is earlier than 2024-01-01, the entire row group (millions of rows) is skipped without decompressing or reading data pages from disk.
4. **Engines and Compression:**
   - `pyarrow` (default, standard) vs `fastparquet`.
   - Compression codecs: `'snappy'` (default, lightning-fast decompression, optimal for analytical speed), `'zstd'` (superior compression ratio), `'gzip'`, `'brotli'`.

#### 2.5 Binary Object Serialization: Pickle (`read_pickle()` and `to_pickle()`)
Python's `pickle` module serializes arbitrary Python objects into a binary byte stream:
- **Exact Schema Preservation:** Preserves exact Pandas dtypes, categorical category orders, MultiIndex hierarchies, and timezone metadata without any parsing ambiguity.
- **Speed:** Faster than CSV and Excel for local prototyping.
- **The Critical Security Warning:** `pickle` executes arbitrary Python code during deserialization. **Never load an untrusted `.pkl` or `.pickle` file** received over a public network, as malicious byte sequences can execute arbitrary shell commands via `os.system`.
- **Cross-Version Incompatibility:** Pickled DataFrames created in Pandas 2.x may fail to deserialize in Pandas 1.x or across differing Python minor versions.

### 3. Fresher Interview Questions

#### 3.1 20 Basic Interview Questions (4-Part Structure)

##### Q1: What is the primary difference between `read_json()` and `pd.json_normalize()`?
- **Concept:** Ingesting flat versus hierarchical JSON.
- **Direct Answer:** `pd.read_json()` parses flat, structured JSON strings or files into a DataFrame based on standard orientation rules. `pd.json_normalize()` is a specialized function designed to flatten deeply nested or semi-structured JSON dictionaries and lists into a tabular 2D DataFrame.
- **Code Example:**
  ```python
  import pandas as pd

  # Flat JSON
  df_flat = pd.read_json('[{"a": 1, "b": 2}]')

  # Nested JSON flattened
  nested = [{"user": "Alice", "details": {"age": 28, "city": "London"}}]
  df_norm = pd.json_normalize(nested)
  print(df_norm.columns.tolist())  # ['user', 'details.age', 'details.city']
```
- **Pitfall / Note:** Calling `read_json()` on nested JSON loads the nested dictionary as an unparsed `dict` object inside a single Series cell rather than unpacking it into separate columns.

##### Q2: What does `orient='records'` mean when reading or writing JSON?
- **Concept:** JSON serialization orientation.
- **Direct Answer:** `orient='records'` treats the JSON payload as a flat list of dictionaries, where each dictionary represents a single row and keys represent column names: `[{"col1": val1, "col2": val2}, ...]`.
- **Code Example:**
  ```python
  df = pd.DataFrame({"name": ["Alice", "Bob"], "score": [95, 88]})
  json_str = df.to_json(orient="records")
  print(json_str)
  # [{"name":"Alice","score":95},{"name":"Bob","score":88}]
```
- **Pitfall / Note:** The default orient for `to_json()` is `'columns'`, not `'records'`. Omitting `orient='records'` when generating payloads for web APIs usually results in rejected requests.

##### Q3: What is JSON Lines (NDJSON), and how do you read it in Pandas?
- **Concept:** Streaming newline-delimited JSON.
- **Direct Answer:** JSON Lines is a format where each line in the text file is a complete, valid JSON object separated by a newline (`\n`). You read it in Pandas by setting `lines=True` in `pd.read_json()`.
- **Code Example:**
  ```python
  df = pd.read_json("api_events.jsonl", lines=True)
```
- **Pitfall / Note:** If `lines=True` is omitted when reading a JSON Lines file, Pandas treats the file as one giant JSON document and raises `ValueError: Trailing data`.

##### Q4: How do you stream a massive 10 GB JSON Lines file without causing an Out-Of-Memory (OOM) error?
- **Concept:** Out-of-core streaming with `chunksize`.
- **Direct Answer:** Combine `lines=True` with `chunksize=N` in `pd.read_json()`. This returns a `JsonReader` iterator that yields DataFrames of $N$ rows per iteration.
- **Code Example:**
  ```python
  total_users = 0
  for chunk in pd.read_json("big_logs.jsonl", lines=True, chunksize=50_000):
    total_users += chunk["user_id"].nunique()
```
- **Pitfall / Note:** `chunksize` only works when `lines=True`. Standard JSON cannot be parsed in streaming chunks because the entire document is wrapped in a single enclosing bracket.

##### Q5: What library does `pd.read_html()` use by default, and what does it return?
- **Concept:** HTML table scraping.
- **Direct Answer:** `pd.read_html()` uses `lxml` (or `html5lib`/`bs4`) to parse HTML. It returns a **Python list of DataFrames** (`list[pd.DataFrame]`), where each DataFrame corresponds to one `<table>` tag discovered in the document.
- **Code Example:**
  ```python
  tables = pd.read_html("https://en.wikipedia.org/wiki/List_of_countries")
  print(f"Discovered {len(tables)} tables.")
  first_table = tables[0]
```
- **Pitfall / Note:** Candidates often assume `read_html()` returns a single DataFrame. If you try to call `.head()` directly on the returned list, Python raises `AttributeError: 'list' object has no attribute 'head'`.

##### Q6: How do you target a specific HTML table on a web page containing dozens of tables?
- **Concept:** Table matching with `match`.
- **Direct Answer:** Use the `match` parameter in `pd.read_html()`, passing a string or regular expression. Pandas parses only tables that contain matching text.
- **Code Example:**
  ```python
  # Extracts only tables containing the phrase "Quarterly Revenue"
  targeted_tables = pd.read_html(
      "https://example.com/finance", match="Quarterly Revenue"
  )
```
- **Pitfall / Note:** If no table matches the string, Pandas raises `ValueError: No tables found matching pattern`.

##### Q7: What is the difference between `read_sql_query()` and `read_sql_table()`?
- **Concept:** Relational database ingestion methods.
- **Direct Answer:** `read_sql_query()` accepts a raw SQL `SELECT` string and executes it directly against the database. `read_sql_table()` accepts a table name and uses SQLAlchemy metadata reflection to fetch the entire table schema and data.
- **Code Example:**
  ```python
  from sqlalchemy import create_engine

  engine = create_engine("sqlite:///company.db")

  # Query-based read (allows filtering and aggregation)
  df_filtered = pd.read_sql_query(
      "SELECT * FROM sales WHERE amount > 100", engine
  )

  # Full table read
  df_all = pd.read_sql_table("sales", engine)
```
- **Pitfall / Note:** `read_sql_table()` requires a SQLAlchemy engine and cannot be used with a raw DBAPI connection.

---

##### Q8: What does `if_exists` control in `DataFrame.to_sql()`?
- **Concept:** Database table insertion behavior.
- **Direct Answer:** `if_exists` dictates what happens if the target database table already exists. Options are `'fail'` (raise ValueError, default), `'replace'` (drop the table and recreate it), and `'append'` (insert new rows into the existing table).
- **Code Example:**
  ```python
  # Append new transaction batch to existing database table
  df.to_sql("audit_log", con=engine, if_exists="append", index=False)
```
- **Pitfall / Note:** Be careful with `if_exists='replace'`: it drops the existing table entirely, destroying primary keys, indexes, foreign key constraints, and column data types defined in the database.

---

##### Q9: Why is `method='multi'` recommended when writing large DataFrames to SQL?
- **Concept:** High-throughput batch SQL insertion.
- **Direct Answer:** By default (`method=None`), Pandas inserts records one row at a time via individual `INSERT` statements, resulting in massive network latency. Setting `method='multi'` generates multi-row values syntax (`INSERT INTO table VALUES (...), (...), ...`), writing thousands of rows per network round-trip.
- **Code Example:**
  ```python
  df.to_sql(
      "transactions",
      con=engine,
      if_exists="append",
      index=False,
      chunksize=2000,
      method="multi",
  )
```
- **Pitfall / Note:** Some database drivers (e.g. SQLite) have a limit on the maximum number of SQL parameters per statement. Setting `chunksize` too high with `method='multi'` can trigger a "too many SQL variables" error.

##### Q10: What is Apache Parquet, and why is it preferred over CSV for analytical pipelines?
- **Concept:** Columnar storage format advantages.
- **Direct Answer:** Parquet is an open-source, columnar binary storage format. It is preferred over CSV because: (1) it provides column pruning (reading only requested columns), (2) predicate pushdown (skipping irrelevant row groups via metadata min/max statistics), (3) built-in Snappy/Zstandard compression, and (4) strict schema and data type preservation.
- **Code Example:**
  ```python
  # Writing to Parquet
  df.to_parquet("analytics.parquet", engine="pyarrow", compression="snappy")

  # Reading only 2 columns with predicate pushdown
  df_pruned = pd.read_parquet(
      "analytics.parquet",
      columns=["user_id", "revenue"],
      filters=[("revenue", ">", 1000)],
  )
```
- **Pitfall / Note:** Unlike CSV, Parquet is a binary format and cannot be inspected in a standard plain text editor.

---

##### Q11: What is "column pruning" in Parquet, and how do you achieve it in `pd.read_parquet()`?
- **Concept:** Columnar projection optimization.
- **Direct Answer:** Column pruning means the reader only loads the specific byte offsets for requested columns from disk into memory, completely ignoring unselected columns. In Pandas, pass the list of needed columns to the `columns` parameter in `pd.read_parquet()`.
- **Code Example:**
  ```python
  # If the file has 300 columns, only these 2 are read from disk
  df_sub = pd.read_parquet("wide_data.parquet", columns=["cust_id", "status"])
```
- **Pitfall / Note:** In CSV, passing `usecols` still requires streaming all bytes of every row through CPU memory to find delimiters. In Parquet, unselected columns are never touched on disk.

---

##### Q12: What is "predicate pushdown" in Parquet?
- **Concept:** Metadata-level row group filtering.
- **Direct Answer:** Predicate pushdown pushes query filters down to the storage engine level. The reader checks the min/max statistics stored in the Parquet file's metadata footer for each row group. If a row group's values cannot satisfy the condition, the entire row group is skipped without decompression or reading data pages.
- **Code Example:**
  ```python
  # Skips row groups where year != 2024 entirely
  df_filtered = pd.read_parquet(
      "sales.parquet", filters=[("year", "==", 2024)]
  )
```
- **Pitfall / Note:** Predicate pushdown requires the underlying engine (such as `pyarrow`) to support dataset filtering.

---

##### Q13: What are the two primary backend engines for reading and writing Parquet in Pandas?
- **Concept:** Parquet engine dependencies.
- **Direct Answer:** The two primary engines are `pyarrow` (Apache Arrow's C++ library, default and recommended) and `fastparquet` (a Python-based implementation using Numba).
- **Code Example:**
  ```python
  df = pd.read_parquet("data.parquet", engine="pyarrow")
```
- **Pitfall / Note:** `pyarrow` provides superior performance, better support for complex nested schemas, and native compatibility with modern Arrow data backends in Pandas 2.0.

##### Q14: What is the critical security danger of using `pd.read_pickle()`?
- **Concept:** Insecure deserialization vulnerabilities.
- **Direct Answer:** Python's `pickle` format is not secure against untrusted data. When deserializing a pickle file, the Python interpreter executes code specified by the byte stream. Loading an untrusted pickle file can execute malicious system commands (e.g. `rm -rf /` or remote shell injection).
- **Code Example:**
  ```python
  # DANGEROUS: Never do this with untrusted files downloaded from the web
  df = pd.read_pickle("untrusted_download.pkl")
```
- **Pitfall / Note:** Never use pickle for public data interchange or public-facing API endpoints. Use Parquet, JSON, or CSV instead.

##### Q15: Why might a pickled DataFrame fail to load across different Python or Pandas versions?
- **Concept:** Binary protocol version divergence.
- **Direct Answer:** `pickle` serializes the exact internal Python class structures and byte layouts. If Pandas modifies an internal data structure between major versions (e.g. internal BlockManager changes between 1.x and 2.x), unpickling in the newer version raises `ModuleNotFoundError`, `AttributeError`, or loads corrupted objects.
- **Code Example:**
  ```python
  # May raise AttributeError when opened on a different Pandas minor release
  df.to_pickle("model_cache.pkl")
```
- **Pitfall / Note:** For long-term analytical storage, always use standardized open formats like Parquet, not Pickle.

##### Q16: How do you serialize dates as ISO 8601 strings when calling `df.to_json()`?
- **Concept:** Controlling JSON date serialization.
- **Direct Answer:** Specify `date_format='iso'` in `df.to_json()`.
- **Code Example:**
  ```python
  df = pd.DataFrame({"time": pd.to_datetime(["2024-01-15 10:30:00"])})
  print(df.to_json(orient="records", date_format="iso"))
  # [{"time":"2024-01-15T10:30:00.000Z"}]
```
- **Pitfall / Note:** By default, `to_json()` formats timestamps as integer epoch milliseconds (`date_format='epoch'`), which produces numeric values like `1705314600000` rather than human-readable dates.

##### Q17: How do you extract deeply nested record arrays using `record_path` in `pd.json_normalize()`?
- **Concept:** Unnesting child arrays with `pd.json_normalize()`.
- **Direct Answer:** Pass the path to the list of dictionaries as a list of strings to `record_path`. To retain parent-level attributes, pass them to `meta`.
- **Code Example:**
  ```python
  data = [{
      "school": "West High",
      "students": [
          {"name": "Alice", "grade": 11},
          {"name": "Bob", "grade": 12},
      ],
  }]
  df = pd.json_normalize(data, record_path=["students"], meta=["school"])
  print(df)
  #     name  grade     school
  # 0  Alice     11  West High
  # 1    Bob     12  West High
```
- **Pitfall / Note:** Omitting `record_path` leaves the entire list of students as a Python `list` object inside a single cell.

##### Q18: What compression algorithms are supported for Parquet files in Pandas?
- **Concept:** Parquet compression options.
- **Direct Answer:** Common supported algorithms are `'snappy'` (default, fast decompression), `'gzip'` (higher compression ratio, slower), `'brotli'`, `'zstd'` (modern balanced high-ratio codec), and `None` (uncompressed).
- **Code Example:**
  ```python
  df.to_parquet("compressed.parquet", compression="zstd")
```
- **Pitfall / Note:** Snappy is the industry standard default because its decompression speed allows multi-threaded query engines to decompress data faster than disk read speeds.

##### Q19: How do you pass SQL query parameters safely using `read_sql()` to prevent SQL injection?
- **Concept:** Parameterized SQL queries in Pandas.
- **Direct Answer:** Use query parameter placeholders (`:param` in SQLAlchemy) and pass a dictionary of parameters to the `params` argument in `pd.read_sql()` or `pd.read_sql_query()`.
- **Code Example:**
  ```python
  query = "SELECT * FROM users WHERE status = :status_val AND age >= :min_age"
  df = pd.read_sql_query(
      query, con=engine, params={"status_val": "ACTIVE", "min_age": 21}
  )
```
- **Pitfall / Note:** Never use Python f-strings to inject user inputs directly into SQL queries (`f"SELECT * FROM users WHERE status = '{val}'"`), as this introduces critical SQL injection vulnerabilities.

#### 3.2 20 Intermediate Interview Questions

1. **How does `pd.json_normalize()` handle nested keys with custom separators?**  
   It defaults to dot notation (e.g. `'user.address.city'`). You can customize this by passing `sep='_'`, producing snake_case column names like `'user_address_city'`.
2. **What is the difference between `orient='split'` and `orient='records'` in `to_json()`?**  
   `'records'` outputs a list of dictionaries with repeating column name keys on every record, increasing payload size. `'split'` outputs a single dictionary containing separate lists for `columns`, `index`, and `data`, eliminating repetitive key names and reducing JSON payload size by 30% to 50%.
3. **How can you read an HTML table where numbers contain commas and currency symbols?**  
   Pass `thousands=','` and `decimal='.'` to `pd.read_html()`. For currency symbols, you typically clean the resulting string column post-ingestion with `.str.replace('$', '').astype(float)`.
4. **Why is SQLAlchemy 2.0+ engine handling different from legacy Pandas SQL methods?**  
   Legacy Pandas allowed passing raw DBAPI connection objects or string connection URLs directly. SQLAlchemy 2.0 enforces explicit connection contexts (`with engine.connect() as con:`) and explicit `text()` wrappers for raw SQL statements.
5. **How does `pd.read_sql()` determine column data types from a database table?**  
   When connecting via SQLAlchemy, Pandas inspects the database engine's column types (e.g., `VARCHAR`, `INTEGER`, `TIMESTAMP`, `NUMERIC`) and maps them to appropriate NumPy/Pandas dtypes automatically.
6. **What is a Parquet Row Group, and why does its size matter?**  
   A Row Group is a logical horizontal partition of data containing a fixed number of rows (typically 100,000 to 1,000,000 rows). Columns within a row group are stored together. Larger row groups improve compression and sequential scan efficiency; smaller row groups allow more granular predicate pushdown skipping.
7. **What happens if you try to save a DataFrame with mixed data types in a single column to Parquet?**  
   Parquet strictly enforces homogeneous typed columns. If an `object` column contains mixed integers and strings, `pyarrow` raises an `ArrowTypeError` or `ArrowInvalid` error during serialization unless explicitly coerced.
8. **How do you read a partition-structured Parquet dataset (Hive-style partitioning)?**  
   Point `pd.read_parquet()` to the parent directory containing partition folders (e.g., `data/year=2024/month=05/`). PyArrow discovers the directory structure and automatically reconstructs `year` and `month` as categorical columns in the DataFrame.
9. **How do you append rows to an existing Parquet file on disk?**  
   Parquet files are immutable columnar containers; you cannot append rows directly to an existing `.parquet` file without rewriting it. To append, either write a new partition file in the same directory (e.g. `part-00002.parquet`) or read the existing file, concatenate in memory, and rewrite.
10. **What is `fastparquet`, and when might it be chosen over `pyarrow`?**  
    `fastparquet` is a lightweight Python-focused Parquet library that compiles via Numba. It is occasionally chosen in environments where compiled C++ Arrow binaries cannot be easily installed, though `pyarrow` remains the faster and more feature-complete standard.
11. **How can you read a JSON file hosted at an HTTPS URL directly into a DataFrame?**  
    Pass the HTTPS URL string directly to `pd.read_json("https://api.example.com/data.json")`. Pandas handles HTTP requests, buffering, and decompression automatically.
12. **What does `errors='ignore'` vs `'raise'` do in `pd.json_normalize()`?**  
    `errors='raise'` crashes if a specified `meta` key is missing from a dictionary record. `errors='ignore'` fills missing meta values with `NaN`, allowing robust parsing of heterogeneous JSON payloads.
13. **Can `read_sql()` stream records from a database using server-side cursors?**  
    Yes. Setting `chunksize=N` with a SQLAlchemy engine configures server-side execution cursors, fetching $N$ records at a time from the database server and keeping application memory constant.
14. **How do you write a DataFrame with timezone-aware datetimes to SQL?**  
    Ensure the target database supports timezone types (e.g. `TIMESTAMP WITH TIME ZONE` in PostgreSQL). SQLAlchemy will map `datetime64[ns, UTC]` to the proper SQL column type. In SQLite, timestamps are serialized as ISO 8601 strings.
15. **Why is `pickle` unsuited for microservice REST APIs?**  
    Pickle is Python-specific and cannot be consumed by services written in Java, Go, TypeScript, or C#. Furthermore, it presents critical remote code execution security vulnerabilities. JSON or Protocol Buffers are the standard for microservices.
16. **How do you specify exact SQL column types during `to_sql()`?**  
    Pass a dictionary mapping column names to SQLAlchemy types using the `dtype` parameter in `df.to_sql(..., dtype={'code': sqlalchemy.types.VARCHAR(10)})`.
17. **What is the difference between `read_json(..., orient='split')` and standard Python `json.loads`?**  
    `pd.read_json()` parses the string directly in C/compiled routines into contiguous NumPy/Arrow arrays. `json.loads()` constructs a massive tree of standard Python dictionaries, integers, and strings on the Python heap, consuming 4x to 8x more RAM before DataFrame construction.
18. **How does `pd.read_html()` handle merged header cells (`colspan` and `rowspan`)?**  
    Modern versions of `read_html()` parse `colspan` and `rowspan` attributes to construct hierarchical MultiIndex headers, repeating spanned values across columns or rows.
19. **How do you configure Parquet dictionary encoding for string columns?**  
    PyArrow automatically enables dictionary encoding for string columns by default, replacing repetitive strings with compact integer pointers. In Pandas, converting string columns to `category` dtype prior to saving ensures maximum dictionary compression.
20. **What is the performance difference between Snappy and Zstandard compression in Parquet?**  
    Snappy delivers exceptional decompression speed (1-2 GB/s per CPU core), prioritizing query throughput over file size. Zstandard (`zstd`) achieves 20% to 40% higher compression ratios with competitive decompression speed, making it optimal for long-term cold storage.

## Phase 2: High-Yield Concepts, Pitfalls & Production Drills

### 4. Top Questions to Definitely Prepare

#### 4.1 Must-Know Core Questions

1. **How does `pd.json_normalize()` flatten nested JSON structures?**  
   - It recursively unpacks nested dictionary keys into dot-separated column names (e.g. `'user.address.city'`) and extracts nested lists of child records into individual rows via the `record_path` argument, while retaining parent-level attributes via `meta`.
2. **What is the difference between standard JSON and JSON Lines (NDJSON) in terms of memory efficiency?**  
   - Standard JSON requires loading the entire file into memory as a single root object (`[...]` or `{...}`). JSON Lines writes one independent JSON object per line (`\n`), allowing chunked, streaming ingestion via `lines=True` and `chunksize=N` with bounded memory.
3. **Why is Apache Parquet significantly faster than CSV for analytical queries?**  
   - Parquet is columnar rather than row-oriented. It enables column pruning (reading only needed columns from disk) and predicate pushdown (skipping irrelevant row groups using metadata min/max statistics), combined with dictionary encoding and Snappy compression.
4. **How do you execute parameterized SQL queries in `pd.read_sql_query()` to prevent SQL injection?**  
   - Pass parameter placeholders (`:param_name`) in the SQL string and supply a parameters dictionary to the `params` argument: `pd.read_sql_query(query, con=engine, params={'status': 'ACTIVE'})`.
5. **Why should `pickle` never be used to deserialize data from untrusted sources?**  
   - Python's `pickle` format executes arbitrary code during object reconstruction via the `__reduce__` method. A malicious actor can craft a payload that executes arbitrary operating system commands upon unpickling.

#### 4.2 Good-to-Know Differentiating Questions

6. **What is the performance benefit of setting `method='multi'` in `df.to_sql()`?**  
   - By default, Pandas issues individual single-row `INSERT` statements, causing high network round-trip overhead. `method='multi'` constructs batch multi-value inserts (`INSERT INTO table VALUES (...), (...), ...`), accelerating write throughput by 10x to 50x.
7. **How does `pd.read_html()` identify and extract tables from a web page?**  
   - It parses the HTML DOM tree using `lxml` or `html5lib`, extracts all `<table>` elements, converts `<tr>` and `<td>`/`<th>` tags into DataFrame rows and columns, and returns a Python list of DataFrames.
8. **What does `orient='split'` achieve in `df.to_json()`?**  
   - It outputs a single dictionary containing separate lists for `index`, `columns`, and `data`. Unlike `'records'`, which repeats column names for every row, `'split'` eliminates key duplication, reducing payload size by 30% to 50%.
9. **How does Parquet predicate pushdown work at the storage engine level?**  
   - Parquet file footers contain metadata blocks recording the minimum and maximum values for each column in each row group. If a query filter falls outside this min/max range, the query engine skips reading and decompressing that entire row group.
10. **What is the difference between `read_sql_table()` and `read_sql_query()`?**  
    - `read_sql_table()` reflects the schema of a database table directly via SQLAlchemy metadata and fetches all rows/columns. `read_sql_query()` executes a custom SQL statement allowing arbitrary projections, joins, and filters.

#### 4.3 Advanced / Senior / Architect-Level Questions

11. **How do you design a high-throughput data pipeline that ingests hundreds of gigabytes of streaming NDJSON web logs into an analytics lakehouse?**  
    - Stream JSON Lines files in bounded chunks using `pd.read_json(chunksize=100_000, lines=True)`. In each chunk, enforce strict schema casting, convert high-cardinality strings to categories, normalize nested device metadata via `json_normalize`, and write partitioned Snappy-compressed Parquet files to object storage using PyArrow.
12. **Explain the internal architectural trade-offs between `pyarrow` and `fastparquet` as Parquet storage engines.**  
    - `pyarrow` is implemented in C++ and part of the broader Apache Arrow ecosystem. It provides multi-threaded SIMD decoding, zero-copy memory transfers, dataset-level partitioning, and rich complex type support. `fastparquet` is a pure-Python/Numba implementation; while lighter to install, it lacks native SIMD acceleration and has slower predicate pushdown evaluation.
13. **How do you handle schema evolution (e.g. added or renamed columns) across thousands of Parquet files in a partitioned directory?**  
    - Configure PyArrow's dataset scanner with schema evolution options (`pyarrow.dataset.dataset(..., schema=...)`). PyArrow reconciles missing columns by inserting null values and coerces compatible numeric promotions, avoiding pipeline failures.
14. **Why does calling `to_sql()` with `if_exists='replace'` present high architectural risks in production?**  
    - `if_exists='replace'` issues a `DROP TABLE` command followed by `CREATE TABLE`. This permanently deletes custom database indexes, primary key constraints, foreign key cascades, column comments, triggers, and granular user permissions previously configured by database administrators.
15. **How can you optimize web scraping with `pd.read_html()` when websites load tabular data asynchronously via client-side JavaScript?**  
    - `pd.read_html()` is an HTTP and HTML parser; it does not execute client-side JavaScript. For dynamic single-page applications (SPAs), you must either intercept the underlying JSON API network request directly (using `requests` or `httpx` and `pd.read_json()`) or render the page DOM using a headless browser (Playwright or Selenium) before passing the page source to `pd.read_html()`.

### 6. Section-Adaptive Pandas API Confusions

#### Confusion 1: `pd.read_json()` vs `pd.json_normalize()`

| Dimension | `pd.read_json()` | `pd.json_normalize()` |
|:---|:---|:---|
| **Primary Input** | JSON file path, URL, or JSON formatted string. | In-memory Python `dict` or `list` of dictionaries. |
| **Schema Handling** | Expects flat tabular data matching standard orientations. | Purpose-built for deeply nested, semi-structured schemas. |
| **Child Array Unpacking**| Leaves nested lists as Python objects in single cells. | Unrolls nested arrays into rows via `record_path`. |
| **Metadata Retention** | Cannot pull parent fields into child rows. | Pulls ancestor fields into unnested rows via `meta`. |
| **Best Used For** | Flat files, JSON Lines log streams (`lines=True`). | Complex REST API responses, webhooks, MongoDB documents. |

```python
import pandas as pd

# pd.read_json: flat log stream
df_logs = pd.read_json("events.jsonl", lines=True)

# pd.json_normalize: nested API response
payload = [{"org": "Acme", "teams": [{"name": "Dev"}, {"name": "Ops"}]}]
df_teams = pd.json_normalize(payload, record_path=["teams"], meta=["org"])
```

#### Confusion 2: `read_sql()` vs `read_sql_query()` vs `read_sql_table()`

| Function | Argument Accepted | Underlying Mechanism | Primary Use Case |
|:---|:---|:---|:---|
| `pd.read_sql_query()` | SQL query string (`SELECT ...`). | Directly executes query via DB connection. | Filtered subsets, aggregations, joins, complex queries. |
| `pd.read_sql_table()` | Table name string (`'sales'`). | Uses SQLAlchemy Table reflection. | Ingesting entire database tables with exact schema reflection. |
| `pd.read_sql()` | Query string OR Table name. | Delegates to `read_sql_query` or `read_sql_table`. | Generic wrapper for dynamic execution. |

```python
from sqlalchemy import create_engine

engine = create_engine("sqlite:///app.db")

# read_sql_query for analytical filter
df_high = pd.read_sql_query("SELECT * FROM orders WHERE amount > 500", con=engine)

# read_sql_table for complete table mirror
df_all = pd.read_sql_table("orders", con=engine)
```

#### Confusion 3: `pyarrow` vs `fastparquet`

| Dimension | `pyarrow` | `fastparquet` |
|:---|:---|:---|
| **Backing Technology** | Apache Arrow C++ core. | Python with Numba compilation. |
| **Throughput & Speed** | High (SIMD accelerated, multi-threaded). | Moderate (single-threaded default). |
| **Zero-Copy Transfers** | Yes (integrates natively with Arrow backends). | No. |
| **Complex Nested Types** | Complete support for Structs, Lists, Maps. | Limited nested type support. |
| **Industry Standard** | **Yes** (Default in Pandas and PySpark). | Specialized fallback environments. |

---

#### Confusion 4: `orient='records'` vs `'split'` vs `'columns'`

| Orient Setting | JSON Structure Format | Size Efficiency | Typical Consumer |
|:---|:---|:---|:---|
| `'records'` | `[{"colA": 1, "colB": 2}, ...]` | Low (keys repeat per row). | REST APIs, JavaScript UI components. |
| `'split'` | `{"columns": [...], "index": [...], "data": [[...]]}` | High (keys defined once). | High-speed Python-to-Python microservices. |
| `'columns'` | `{"colA": {"0": 1, "1": 3}, "colB": {"0": 2, "1": 4}}` | Moderate. | Default Pandas orientation; rarely used externally. |

---

#### Confusion 5: Parquet vs Pickle vs CSV

| Feature | Apache Parquet | Python Pickle | CSV |
|:---|:---|:---|:---|
| **Storage Structure** | Columnar binary. | Row-based Python byte stream. | Row-oriented plain text. |
| **Type Preservation** | **Strict & Exact** (native schema). | **Exact** (all Python types). | **None** (infers on read). |
| **Security** | Safe (pure data container). | **Unsafe** (arbitrary code execution). | Safe (plain text). |
| **Cross-Language** | Universal (Python, Java, Go, C++, SQL). | Python only. | Universal plain text. |
| **Compression Ratio** | High (Snappy / Zstd). | Moderate. | None (unless zipped). |
| **Query Speed** | Fastest (column pruning + pushdown). | Fast. | Slowest (full file parse). |

### 7. Interview Traps (10 Traps)

#### Trap 1: The Invisible List in `read_html()`
- **The Trap:** An interviewer asks you why `pd.read_html('https://example.com/data')[['Name', 'Score']]` crashes with `TypeError: list indices must be integers or slices, not list`.
- **Why It Catches Candidates:** Candidates forget that `read_html()` returns a Python `list` containing all tables discovered in the HTML document.
- **The Reality / Mechanics:** You must access the target element by index first: `tables[0][['Name', 'Score']]`.
- **How to Avoid:** Always assign to `tables = pd.read_html(...)` and extract `tables[0]`.

---

#### Trap 2: The Silent Table Destruction of `if_exists='replace'`
- **The Trap:** An interviewer asks: "We want to update our PostgreSQL `users` table with fresh daily records using `to_sql()`. Should we use `if_exists='replace'`?"
- **Why It Catches Candidates:** Candidates assume `'replace'` works like SQL `TRUNCATE` or `DELETE`, refreshing table contents.
- **The Reality / Mechanics:** `to_sql(if_exists='replace')` executes `DROP TABLE users`. All primary keys, foreign key constraints, indexes, and database permissions are permanently destroyed.
- **How to Avoid:** Use `if_exists='append'` after executing an explicit `TRUNCATE TABLE` statement via SQLAlchemy.

---

#### Trap 3: The Untrusted Pickle Security Vulnerability
- **The Trap:** An interviewer asks: "A third-party vendor sends us a 5 GB `.pkl` file via an unsecured S3 bucket. How should we load it into Pandas?"
- **Why It Catches Candidates:** Candidates discuss memory optimization, chunking, or multithreading.
- **The Reality / Mechanics:** The correct answer is **DO NOT LOAD IT**. Pickle files can contain weaponized `__reduce__` payloads that execute remote shell commands upon deserialization. The vendor must provide Parquet, CSV, or JSON.
- **How to Avoid:** Identify pickle as an untrusted security risk and insist on an open columnar format.

---

#### Trap 4: The Truncated Parameter Crash in SQLite
- **The Trap:** Calling `df.to_sql('data', con=sqlite_engine, chunksize=10000, method='multi')` crashes on a wide DataFrame with `OperationalError: too many SQL variables`.
- **Why It Catches Candidates:** Candidates assume larger chunks always equal faster execution.
- **The Reality / Mechanics:** SQLite has a hardcoded limit of 999 (or 32,766 in newer versions) host parameters per query. If a DataFrame has 50 columns, a chunk of 1,000 rows generates $50 \times 1,000 = 50,000$ variables, exceeding SQLite's limit.
- **How to Avoid:** Calculate `chunksize = max_vars // num_columns` when using `method='multi'`.

---

#### Trap 5: The NDJSON Trailing Data Error
- **The Trap:** Loading a `.json` log file crashes with `ValueError: Trailing data` on row 2.
- **Why It Catches Candidates:** Candidates assume all `.json` files are standard JSON documents.
- **The Reality / Mechanics:** Log files are almost always formatted as JSON Lines (one JSON object per line). Without `lines=True`, the parser expects EOF after parsing the first object on line 1.
- **How to Avoid:** Set `lines=True` when ingesting event logs or streaming telemetry.

---

#### Trap 6: Parquet Column Type Mutability Illusion
- **The Trap:** A candidate tries to save a DataFrame to Parquet where a column contains both integers and string error codes (`[101, 102, 'ERR_TIMEOUT']`).
- **Why It Catches Candidates:** CSV handles mixed types seamlessly as text; candidates expect Parquet to do the same.
- **The Reality / Mechanics:** Parquet enforces strict physical column schemas. PyArrow will reject the DataFrame with an `ArrowTypeError`.
- **How to Avoid:** Clean and homogenize column dtypes before saving to Parquet.

---

#### Trap 7: Missing `meta` Keys in `pd.json_normalize()`
- **The Trap:** An API returns 1,000 records. 995 records have `{"user": {"tier": "gold"}}`, but 5 records omit the `"tier"` key. Calling `json_normalize(..., meta=[['user', 'tier']])` crashes with `KeyError: 'tier'`.
- **Why It Catches Candidates:** Candidates assume missing keys default to `NaN`.
- **The Reality / Mechanics:** `pd.json_normalize()` defaults to `errors='raise'`.
- **How to Avoid:** Set `errors='ignore'` to populate missing meta keys with `NaN`.

---

#### Trap 8: Epoch Milliseconds Date Truncation in JSON
- **The Trap:** An analytics script calls `df.to_json('dates.json')`. When opened in a web dashboard, all timestamps appear as large 13-digit numbers (`1705314600000`).
- **Why It Catches Candidates:** Candidates expect `to_json()` to format dates as ISO strings like `'2024-01-15'`.
- **The Reality / Mechanics:** `df.to_json()` defaults to `date_format='epoch'`.
- **How to Avoid:** Pass `date_format='iso'`.

---

#### Trap 9: Parquet Append Immutability
- **The Trap:** An interviewer asks: "Write code to append 1,000 rows to an existing 10 GB `sales.parquet` file on disk without loading the 10 GB file into memory."
- **Why It Catches Candidates:** Candidates look for an `append=True` or `mode='a'` flag in `df.to_parquet()`.
- **The Reality / Mechanics:** Parquet files are immutable. You cannot append rows to an existing Parquet file without rewriting the entire file.
- **How to Avoid:** Write a new partition file (e.g. `part_0002.parquet`) within the same dataset directory.

---

#### Trap 10: The In-Memory Bloat of `json.loads` vs `pd.read_json`
- **The Trap:** An interviewer asks: "Why not just use `import json; df = pd.DataFrame(json.load(f))` instead of `pd.read_json()`?"
- **Why It Catches Candidates:** Both produce a DataFrame, and Python's built-in `json` module feels intuitive.
- **The Reality / Mechanics:** `json.load()` instantiates millions of standalone Python heap objects (dicts, strings, ints), causing massive memory spikes (4x-8x larger than the file). `pd.read_json()` parses directly into contiguous C/Arrow buffers.
- **How to Avoid:** Use `pd.read_json()` for high performance and bounded memory.

#### Question 1: Ingesting Complex Nested Stripe Webhook Payloads
- **Scenario:** An e-commerce platform receives daily JSON webhook exports from Stripe containing thousands of charge events. Each event contains transaction metadata (`id`, `created`, `currency`), a nested `customer` object (`email`, `country`), and a nested list of `line_items` (`item_id`, `amount`, `quantity`). Build a production normalization pipeline that unpacks each line item into a flat relational row while preserving the parent event metadata, handling missing customer keys gracefully.

  ```python
  import pandas as pd


  def process_stripe_webhooks(webhook_payloads: list[dict]) -> pd.DataFrame:
    # Use json_normalize with record_path and multi-level meta paths
    df = pd.json_normalize(
        webhook_payloads,
        record_path=["line_items"],
        meta=[
            "id",
            "created",
            "currency",
            ["customer", "email"],
            ["customer", "country"],
        ],
        meta_prefix="evt_",
        record_prefix="item_",
        errors="ignore",  # Fills missing customer keys with NaN
    )

    # Standardize column naming
    df.rename(
        columns={
            "evt_id": "event_id",
            "evt_created": "event_timestamp",
            "evt_customer.email": "customer_email",
            "evt_customer.country": "customer_country",
        },
        inplace=True,
    )

    # Ensure timestamp conversion
    if "event_timestamp" in df.columns:
      df["event_timestamp"] = pd.to_datetime(
          df["event_timestamp"], unit="s", utc=True
      )

    return df
```

#### Question 2: High-Performance Database to Parquet Lake Archival
- **Scenario:** You are tasked with migrating a 100-million-row financial ledger table from an OLTP PostgreSQL database to an S3 Parquet data lake. The ETL worker has a strict 4 GB RAM limit. The pipeline must stream records in batches, partition files by `transaction_year` and `status`, compress with Snappy, and ensure exact decimal precision on currency fields.
- **Solution:**
  ```python
  import pandas as pd
  from sqlalchemy import create_engine


  def archive_sql_ledger_to_parquet(
      db_uri: str, target_s3_prefix: str, chunk_size: int = 500_000
  ):
    engine = create_engine(db_uri)
    query = "SELECT transaction_id, account_id, amount::float4 AS amount, status, created_at, EXTRACT(YEAR FROM created_at)::int AS transaction_year FROM financial_ledger"

    with engine.connect().execution_options(
        stream_results=True
    ) as con:  # Server-side cursor
      for idx, chunk_df in enumerate(
          pd.read_sql_query(query, con=con, chunksize=chunk_size)
      ):
        # Downcast integer types
        chunk_df["transaction_year"] = chunk_df["transaction_year"].astype(
            "int16"
        )
        chunk_df["status"] = chunk_df["status"].astype("category")

        # Write partitioned Parquet files
        chunk_df.to_parquet(
            target_s3_prefix,
            engine="pyarrow",
            compression="snappy",
            partition_cols=["transaction_year", "status"],
            index=False,
        )
        print(f"Processed and partitioned chunk {idx + 1} ({len(chunk_df):,} rows)")
```

#### Question 3: Scraping Multi-Page Regulatory Filing Tables
- **Scenario:** A regulatory intelligence service scrapes pharmaceutical trial results published in HTML tables across 50 FDA reporting pages. The HTML pages have complex structures: navigation menus, disclaimer footers, and nested tables. The target trial table always contains the column header "Adverse Event Frequency". Write a robust scraping extractor that retrieves the target table, cleans numeric percentage columns, and ignores non-tabular markup.
- **Solution:**
  ```python
  import pandas as pd


  def scrape_clinical_trials(page_urls: list[str]) -> pd.DataFrame:
    all_trials = []

    for url in page_urls:
      try:
        # Match only tables containing the required clinical header
        tables = pd.read_html(url, match="Adverse Event Frequency")
        if not tables:
          continue

        target_df = tables[0].copy()

        # Flatten MultiIndex headers if created by colspan
        if isinstance(target_df.columns, pd.MultiIndex):
          target_df.columns = [
              "_".join(str(c) for c in col).strip() for col in target_df.columns
          ]

        # Clean string percentages to numeric floats
        for col in target_df.columns:
          if "frequency" in col.lower() or "rate" in col.lower():
            target_df[col] = (
                target_df[col]
                .astype(str)
                .str.replace("%", "", regex=False)
                .str.replace(",", "", regex=False)
            )
            target_df[col] = pd.to_numeric(target_df[col], errors="coerce")

        target_df["source_url"] = url
        all_trials.append(target_df)

      except Exception as err:
        print(f"Warning: Failed to scrape {url} due to {err}")
        continue

    return (
        pd.concat(all_trials, ignore_index=True)
        if all_trials
        else pd.DataFrame()
    )
```

#### Question 4: Predicate Pushdown and Column Pruning Benchmark in Parquet
- **Scenario:** An analytics team queries a 50 GB Parquet dataset containing 500 million records and 80 columns. Analysts frequently query only 3 columns for users located in California (`state == 'CA'`). Write a function demonstrating how to use `columns` and `filters` in `pd.read_parquet()` to execute this query in under 2 seconds while consuming less than 500 MB of RAM.

  ```python
  import pandas as pd


  def fast_filtered_parquet_query(parquet_path: str) -> pd.DataFrame:
```

### 13. Flashcard Section (16 Flashcards)

#### Card 1
- **Front:** What is the fundamental difference between `read_json()` and `pd.json_normalize()`?
- **Back:** `read_json()` parses flat, tabular JSON structures based on standard orientations (`records`, `split`, etc.). `pd.json_normalize()` flattens deeply nested, hierarchical dictionaries and unrolls child arrays into rows via `record_path` while retaining parent metadata via `meta`.

#### Card 2
- **Front:** Why does `pd.read_html()` return a list instead of a single DataFrame?
- **Back:** Webpages and HTML documents frequently contain multiple `<table>` elements (e.g. navigation grids, sidebar widgets, data tables). `read_html()` parses every table found, returning each as an independent DataFrame in a Python `list`.

#### Card 3
- **Front:** What is "Column Pruning" in Apache Parquet?
- **Back:** Because Parquet is a columnar format, each column's data pages are stored contiguously. Passing `columns=['A', 'B']` tells the reader to seek and load only the byte ranges on disk for those two columns, ignoring all other columns completely.

#### Card 4
- **Front:** What is "Predicate Pushdown" in Apache Parquet?
- **Back:** Parquet files contain min/max metadata statistics for each column in each row group footer. When query filters are passed (e.g. `filters=[('age', '>', 30)]`), the storage engine checks metadata first and skips entire row groups without decompressing or reading data pages.

#### Card 5
- **Front:** Why should you avoid `if_exists='replace'` in `to_sql()` on production databases?
- **Back:** `if_exists='replace'` issues a `DROP TABLE` command followed by `CREATE TABLE`. This permanently deletes primary keys, foreign key constraints, indexes, column comments, triggers, and database user permissions. Use `if_exists='append'` instead.

#### Card 6
- **Front:** What is the effect of `method='multi'` in `df.to_sql()`?
- **Back:** Standard `to_sql()` executes individual `INSERT INTO table VALUES (...)` statements row-by-row, causing high latency. `method='multi'` combines thousands of records into batch multi-value statements (`INSERT INTO table VALUES (...), (...), ...`), boosting write throughput by 10x-50x.

#### Card 7
- **Front:** What is JSON Lines (NDJSON) and why is it preferred for big data?
- **Back:** Standard JSON requires a single enclosing root array `[...]`, forcing the entire document into RAM. JSON Lines writes each record as an independent valid JSON string on a single line separated by `\n`, allowing out-of-core streaming via `lines=True, chunksize=N`.

#### Card 8
- **Front:** Why is `to_pickle()` and `read_pickle()` dangerous for public data exchange?
- **Back:** Python's `pickle` protocol can execute arbitrary code during unpickling via `__reduce__`. Deserializing an untrusted pickle file allows attackers to execute shell commands and compromise the host system.

#### Card 9
- **Front:** What does `orient='split'` output in `df.to_json()`?
- **Back:** It serializes the DataFrame into a dictionary with separate keys: `{"columns": [...], "index": [...], "data": [[...]]}`. This eliminates repetitive column name strings for each row, reducing JSON payload size by 30% to 50%.

#### Card 10
- **Front:** What is the difference between `pyarrow` and `fastparquet`?
- **Back:** `pyarrow` is implemented in C++ (part of Apache Arrow), supports multi-threaded SIMD decoding, dataset partitioning, complex nested schemas, and Arrow backends. `fastparquet` is a Python/Numba library; it is lighter to install but slower and less feature-complete.

#### Card 11
- **Front:** How do you handle missing metadata keys in `pd.json_normalize()`?
- **Back:** By default, `pd.json_normalize()` raises `KeyError` if a specified `meta` attribute is missing from any record. Pass `errors='ignore'` to populate missing metadata with `NaN`.

#### Card 12
- **Front:** Why do dates in `to_json()` export as 13-digit numbers by default?
- **Back:** Pandas defaults to `date_format='epoch'`, converting datetimes to epoch milliseconds (e.g. `1705314600000`). To serialize human-readable ISO 8601 strings, specify `date_format='iso'`.

#### Card 13
- **Front:** How does `read_sql_query()` differ from `read_sql_table()`?
- **Back:** `read_sql_query()` executes an arbitrary SQL `SELECT` statement (with joins, aggregations, and where clauses). `read_sql_table()` reflects the entire table schema and data via SQLAlchemy metadata.

#### Card 14
- **Front:** Can you append new records to an existing Parquet file on disk?
- **Back:** No. Parquet files are immutable binary containers. To append data, write a new partition file (e.g. `part_0002.parquet`) within the same partitioned directory.

#### Card 15
- **Front:** How do you handle non-standard thousand separators and currency signs in `read_html()`?
- **Back:** Pass `thousands=','` and `decimal='.'` to `pd.read_html()`. Strip currency symbols post-ingestion using string replacement: `df['col'].str.replace('$', '').astype(float)`.

#### Card 16
- **Front:** Why does SQLite raise `OperationalError: too many SQL variables` with `method='multi'`?
- **Back:** SQLite limits SQL statements to 999 (or 32,766) parameters. If a DataFrame has 50 columns, a chunk of 1,000 rows creates 50,000 variables, exceeding the limit. Set `chunksize = max_vars // num_columns`.

#### Scenario 4: Secure Data Clean Room Ingestion Pipeline
- **Context:** An analytics platform receives external client datasets. Some clients send pickled DataFrames (`.pkl`), while others provide JSON. A security audit flags the pipeline for arbitrary code execution vulnerabilities.

     ```python
     import pyarrow.parquet as pq


     def secure_ingest_client_parquet(
         filepath: str, expected_schema: list[str]
     ) -> pd.DataFrame:
       # Inspect metadata footer without executing Python bytecodes
       parquet_meta = pq.read_metadata(filepath)
       available_cols = parquet_meta.schema.names
       if not set(expected_schema).issubset(set(available_cols)):
         raise ValueError("Schema mismatch in submitted Parquet file.")
       return pd.read_parquet(filepath, columns=expected_schema)
```

### 18. Cross-Concept Bridges

#### 1. Connection to CSV & Excel (Chapter 15.1 & 15.2)
- CSV and Excel are row-oriented formats where adding columns degrades query speed. Parquet is columnar, allowing zero-cost column pruning.
- While Excel is strictly capped at $1,048,576$ rows, Parquet, SQL, and NDJSON handle arbitrarily large datasets spanning billions of rows across partitions.

#### 2. Connection to Memory Optimization (Chapter 1)
- Parquet natively integrates with Apache Arrow. Reading Parquet via `pd.read_parquet(..., dtype_backend='pyarrow')` builds Arrow-backed arrays with bitmasked null tracking, reducing RAM usage by 60% compared to legacy NumPy object backends.

#### 3. Connection to Categorical Data (Chapter 8)
- String columns with repetitive values take massive memory in CSV and JSON. In Parquet, dictionary encoding automatically indexes repeated strings as integers, mimicking Pandas' `category` dtype at the storage level.

#### 4. Connection to Advanced PyArrow Ecosystem (Chapter 24)
- Parquet is the physical file specification of Apache Arrow. Knowing how to manipulate Parquet in Pandas serves as the direct foundation for distributed query engines like DuckDB, Polars, and PySpark.

### 20. What a Fresher Should Understand (Computational Mechanics)

1. **Columnar vs Row-Oriented Storage:**
   - Understand that in CSV/JSON, consecutive bytes represent fields of one row. Loading a single column requires streaming all bytes of all rows through CPU cache.
   - In Parquet, each column's data is stored in contiguous disk pages. Column pruning reads only the byte ranges of requested columns, bypassing the rest.
2. **How Predicate Pushdown Operates:**
   - Understand how Parquet file metadata blocks store `[min_val, max_val]` for each column in each row group.
   - Grasp how query engines evaluate filter clauses against metadata first, skipping millions of non-matching rows without reading data pages.
3. **The Overhead of `json.loads` vs `pd.read_json`:**
   - Recognize that standard Python JSON parsing constructs individual Python heap objects for every key and value, inflating memory 5x.
   - Understand how Pandas and Arrow parse JSON bytes directly into contiguous C-level data buffers.

### 24. Final 2-Minute Revision Summary

- **JSON Lines (NDJSON):** Always use `pd.read_json('file.jsonl', lines=True, chunksize=N)` for streaming log files and event buses.
- **Nested JSON:** Use `pd.json_normalize(payload, record_path=[...], meta=[...], errors='ignore')` to unpack hierarchical API responses into 2D tables.
- **HTML Tables:** `pd.read_html(url, match='...')` parses all `<table>` elements into a Python list of DataFrames using `lxml`.
- **SQL Security:** Always execute parameterized SQL queries using `pd.read_sql_query(text(...), con=engine, params={...})` to prevent SQL injection.
- **High-Throughput SQL Writing:** In `df.to_sql()`, always pass `index=False`, `chunksize=2000`, and `method='multi'` to accelerate insertion by 10x-50x.
- **Parquet Columnar Performance:** Use `pd.read_parquet('data.parquet', columns=[...], filters=[...])` to achieve storage-level column pruning and predicate pushdown.
- **Pickle Security Warning:** Never use `pd.read_pickle()` on untrusted data; pickle execution can trigger remote code execution. Use Parquet for production storage.
