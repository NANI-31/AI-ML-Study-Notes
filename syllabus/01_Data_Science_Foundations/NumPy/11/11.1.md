In NumPy, sorting is not merely an algorithmic exercise in comparison and swapping; it is an intimate interaction between C-level sorting implementations (Introsort, Timsort, Heapsort, Radix Sort), memory layouts (strides, memory contiguity, C-order vs Fortran-order), array mutations (in-place `ndarray.sort()` vs copy-allocating `np.sort()`), and indirect indexing structures (`argsort()`, `lexsort()`, `partition()`).

This module provides exhaustive, production-grade technical interview preparation on NumPy sorting mechanics:
- **Direct Sorting Primitives**: The mechanical differences between functional `np.sort()` (out-of-place copy) and object-method `ndarray.sort()` (in-place buffer mutation).
- **Algorithmic Mechanics & Complexity**: Deep dive into NumPy's sorting engines (`kind='quicksort'` [Introsort], `'mergesort'` [Timsort / stable], `'heapsort'`, and `'stable'`), their time complexities ($O(N \log N)$ worst-case vs average), auxiliary memory consumption ($O(1)$ vs $O(N)$), and numerical stability.
- **Indirect & Multi-Key Indexing**: `argsort()` permutation arrays, row-aligned index gathering (`arr[arr[:, col].argsort()]`), `lexsort()` dictionary order sorting across multi-attribute tabular records, and structured array sorting.
- **Multidimensional & Axis Mechanics**: Element-wise independent sorting along `axis=0` vs `axis=1`, cache eviction dynamics across strided column sorts vs contiguous row sorts, and the critical distinction between sorting rows independently versus reordering entire rows based on a key column.
- **Modern Hardware & NumPy 2.0 Enhancements**: Universal SIMD (AVX-512 / ARM Neon) vectorized sorting (e.g., Google Highway integration), string sorting optimizations, and thread-safety considerations.

## 2. Theoretical Breakdown

### Algorithmic Foundations of NumPy's Sort Engines
NumPy encapsulates multiple sorting algorithms within its C engine (`np.sort(..., kind=...)`):
1. **Introsort (`kind='quicksort'`)**:
   - The default algorithm in NumPy for general numeric arrays.
   - It begins with standard QuickSort (median-of-three pivot selection).
   - If the recursion depth exceeds $2 \lfloor \log_2(N) \rfloor$ (detecting quadratic pathological cases), it automatically switches to **HeapSort**, guaranteeing $O(N \log N)$ worst-case time complexity.
   - For small sub-arrays (length $< 16$), it switches to **Insertion Sort** to maximize CPU instruction pipelining and cache locality.
   - Auxiliary Memory: $O(\log N)$ recursion stack space.
   - Stability: **Unstable** (relative order of identical keys is not preserved).
2. **Timsort / Mergesort (`kind='mergesort'` or `kind='stable'`)**:
   - An adaptive, stable sorting algorithm derived from MergeSort and InsertionSort.
   - Detects natural ordered "runs" in the data, sorting them with insertion sort and merging them in $O(N)$ linear time when data is partially presorted.
   - Worst-case time complexity: $O(N \log N)$; Best-case (pre-sorted): $O(N)$.
   - Auxiliary Memory: $O(N)$ for merging buffers.
   - Stability: **Strictly Stable** (guarantees that identical keys maintain their original relative index positions).
3. **HeapSort (`kind='heapsort'`)**:
   - In-place sorting algorithm based on a binary heap data structure.
   - Worst-case time complexity: $O(N \log N)$ strictly guaranteed.
   - Auxiliary Memory: $O(1)$ constant memory overhead.
   - Stability: **Unstable**.
   - Performance: Slower in practice than Introsort due to poor CPU cache locality (jumping through non-contiguous heap parent-child indices).
4. **Radix Sort**:
   - Utilized under the hood in NumPy for 1D integer and floating-point arrays when `kind='stable'` is specified for types where Radix Sort is applicable.
   - Sorts numbers digit by digit (or byte by byte) using counting sort passes.
   - Complexity: $O(K \cdot N)$ where $K$ is the number of bytes in the data type (e.g., $K=8$ for `int64`).


### Multidimensional Strides & Axis Sorting Mechanics
When sorting an array along an axis, NumPy sorts each 1D slice along that dimension independently:
- **`axis=-1` or `axis=1` (Row-wise sorting in 2D C-order)**:
  - Elements in each row are contiguous in memory (stride $= \text{itemsize}$).
  - Hardware prefetchers load contiguous 64-byte cache lines; sorting algorithms execute at peak hardware efficiency.
- **`axis=0` (Column-wise sorting in 2D C-order)**:
  - Elements in each column are separated by stride $= \text{cols} \times \text{itemsize}$.
  - Every swap or comparison across rows touches a different memory page or cache line, incurring high cache miss penalties.
- **CRITICAL DISTINCTION: Independent Axis Sort vs Whole-Row Reordering**:
  - `arr.sort(axis=0)` sorts each column **independently**. It scrambles the relationship between elements in the same row!
  - To sort entire rows based on the values in a specific key column, one must use indirect indexing: `arr[arr[:, key_col].argsort()]`.

### Q1: What is the fundamental difference between `np.sort(arr)` and `arr.sort()`?
**1. Definition & Core Concept:**
`np.sort(arr)` is a functional API that returns a freshly allocated, sorted **copy** of the array, leaving the input array untouched. `arr.sort()` is an ndarray object method that sorts the underlying memory buffer **in-place**, mutating the array and returning `None`.

**2. Technical & Memory Mechanics:**
`np.sort(arr)` allocates a new `PyArrayObject` and data buffer of size $N \times \text{itemsize}$, copies the source bytes into it, and executes the C-level sorting engine on the newly allocated buffer. Space complexity: $O(N)$. `arr.sort()` checks whether `arr.flags.writeable` is True. If writeable, it executes the C sorting routine directly on the existing pointer `arr->data`, modifying bytes in-place. Space complexity: $O(1)$ auxiliary memory (for quicksort).

**3. Explanatory Code Snippet:**
```python
import numpy as np

# 1. Functional sort: Returns copy, leaves original unchanged
a = np.array([4, 1, 3, 2])
res = np.sort(a)
assert res is not a
assert np.array_equal(res, [1, 2, 3, 4])
assert np.array_equal(a, [4, 1, 3, 2]) # Unchanged!

# 2. Method sort: In-place mutation, returns None
ret = a.sort()
assert ret is None
assert np.array_equal(a, [1, 2, 3, 4]) # Mutated!
```

**4. Interview Nuance / Real-World Pitfall:**
Writing `arr = arr.sort()` is a notorious beginner trap. Because `arr.sort()` returns `None`, this statement permanently overwrites your array variable with `None`!

### Q2: What is `np.argsort()`, and what does its output array represent?
**1. Definition & Core Concept:**
`np.argsort(arr)` performs an indirect sort, returning an array of integer indices (a permutation array) that would sort the original array along the specified axis.

**2. Technical & Memory Mechanics:**
`np.argsort()` does not rearrange values in the input array. Instead, it constructs an index array `idx = np.arange(N, dtype=np.intp)` and sorts the indices by comparing the values in `arr[idx[i]]`. The resulting integer array has `dtype=intp` (64-bit signed integer on 64-bit systems). The element at `argsort()[k]` is the original index of the element that belongs at position `k` in the sorted sequence.

**3. Explanatory Code Snippet:**
```python
import numpy as np

scores = np.array([88, 42, 95, 70])
indices = np.argsort(scores)

print("Sorted indices:  ", indices)         # [1, 3, 0, 2]
print("Reconstructed arr:", scores[indices]) # [42, 70, 88, 95]

assert np.array_equal(scores[indices], np.sort(scores))
```

**4. Interview Nuance / Real-World Pitfall:**
`np.argsort()` allocates a new index array of size $N \times 8$ bytes (for 64-bit systems). For an array of 100 million `int8` elements (100 MB), `argsort()` will allocate an 800 MB index buffer—an 8x memory expansion!

### Q3: What are the four sorting algorithms supported by `kind` in `np.sort()`, and what are their trade-offs?
**1. Definition & Core Concept:**
NumPy supports four `kind` values:
1. `'quicksort'` (Introsort)
2. `'mergesort'` (Timsort)
3. `'heapsort'` (HeapSort)
4. `'stable'` (Timsort / RadixSort)

**2. Technical & Memory Mechanics:**
- `'quicksort'` (Introsort): Average $O(N \log N)$, worst-case $O(N \log N)$, auxiliary memory $O(\log N)$. Unstable. Fastest general-purpose sorter due to cache locality.
- `'mergesort'` / `'stable'`: Average $O(N \log N)$, worst-case $O(N \log N)$, best-case $O(N)$ (if pre-sorted). Auxiliary memory $O(N/2)$ to $O(N)$. Stable.
- `'heapsort'`: Worst-case $O(N \log N)$, auxiliary memory $O(1)$ constant. Unstable. Slower in practice than introsort due to cache misses.

**3. Explanatory Code Snippet:**
```python
import numpy as np

data = np.array([5, 2, 9, 1, 5, 6])

s_quick  = np.sort(data, kind='quicksort')
s_merge  = np.sort(data, kind='mergesort')
s_heap   = np.sort(data, kind='heapsort')
s_stable = np.sort(data, kind='stable')

assert np.array_equal(s_quick, [1, 2, 5, 5, 6, 9])
```

**4. Interview Nuance / Real-World Pitfall:**
In modern NumPy, specifying `kind='mergesort'` is synonymous with `kind='stable'`. For integer arrays, NumPy may automatically employ an optimized Radix Sort under `'stable'`.

### Q4: What does it mean for a sorting algorithm to be "stable", and when is stability mandatory?
**1. Definition & Core Concept:**
A sorting algorithm is **stable** if elements with identical keys retain their original relative order in the sorted output. Stability is mandatory when performing multi-pass sorting or when preserving existing secondary groupings.

**2. Technical & Memory Mechanics:**
Consider structured records `[("Bob", 80), ("Alice", 90), ("Charlie", 80)]`. If sorted by score:
- A **stable** sort guarantees that `"Bob"` appears before `"Charlie"` because `"Bob"` appeared before `"Charlie"` in the input.
- An **unstable** sort (like standard QuickSort/Introsort) may swap `"Bob"` and `"Charlie"` based on pivot choices and memory traversal.

**3. Explanatory Code Snippet:**
```python
import numpy as np

# Structured array with duplicate scores
records = np.array([('Bob', 80), ('Alice', 90), ('Charlie', 80)],
                   dtype=[('name', 'U10'), ('score', 'i4')])

# 1. Stable sort preserves input order of Bob and Charlie
stable_res = np.sort(records, order='score', kind='stable')
assert stable_res['name'][0] == 'Bob'
assert stable_res['name'][1] == 'Charlie'

# 2. In unstable sorts, order of equal keys is not guaranteed
```

**4. Interview Nuance / Real-World Pitfall:**
When sorting indices via `argsort()`, an unstable sort can produce non-deterministic index orderings across different operating systems, CPU architectures, or NumPy versions, breaking regression test assertions. Always use `kind='stable'` when index reproducibility for equal keys is required.

### Q5: How does the `axis` parameter behave in `np.sort()` on multidimensional arrays?
**1. Definition & Core Concept:**
The `axis` parameter specifies the dimension along which elements are sorted. By default, `axis=-1` (the last axis, sorting along rows in 2D C-order). Setting `axis=None` flattens the array into a 1D array before sorting.

**2. Technical & Memory Mechanics:**
For a 2D array of shape $(M, N)$:
- `axis=1` (or `axis=-1`): Sorts each of the $M$ rows independently. The elements within each row are reordered; elements never cross row boundaries.
- `axis=0`: Sorts each of the $N$ columns independently. Elements within each column are reordered; elements never cross column boundaries.
- `axis=None`: Allocates a new 1D array of size $M \times N$, flattens all elements, and sorts them globally.

**3. Explanatory Code Snippet:**
```python
import numpy as np

mat = np.array([
    [9, 2, 5],
    [1, 8, 3]
])

# Sort along last axis (each row sorted independently)
row_sorted = np.sort(mat, axis=1)
print("Row sorted:
", row_sorted)
# [[2, 5, 9],
#  [1, 3, 8]]

# Sort along axis 0 (each column sorted independently)
col_sorted = np.sort(mat, axis=0)
print("Col sorted:
", col_sorted)
# [[1, 2, 3],
#  [9, 8, 5]]

# Global sort (flattened)
global_sorted = np.sort(mat, axis=None)
print("Global sorted:
", global_sorted) # [1, 2, 3, 5, 8, 9]
```

**4. Interview Nuance / Real-World Pitfall:**
Unlike Python's built-in `sorted()` which flattens nested iterables, `np.sort(mat)` defaults to `axis=-1`, NOT `axis=None`! Developers expecting a global sort are surprised to find each row sorted independently.

### Q6: How do you sort an entire 2D table by the values in a specific column without scrambling row integrity?
**1. Definition & Core Concept:**
To sort whole rows based on the values in column $k$, you compute the permutation indices of column $k$ using `np.argsort()` and apply fancy indexing along the row dimension: `table[table[:, k].argsort()]`.

**2. Technical & Memory Mechanics:**
`table[:, k]` extracts a 1D view of column $k$. `np.argsort()` returns a 1D array of row indices that sort that column. Applying `table[sort_indices]` invokes fancy indexing along axis 0, which reorders complete rows intact, preserving the horizontal relationship between all columns in each row.

**3. Explanatory Code Snippet:**
```python
import numpy as np

# Table: [ID, Age, Salary]
table = np.array([
    [101, 35, 75000],
    [102, 24, 50000],
    [103, 29, 90000],
    [104, 42, 60000]
])

# Sort entire table by Age (Column 1)
age_col = table[:, 1]
sort_order = np.argsort(age_col)
sorted_table = table[sort_order]

print("Sorted by Age:
", sorted_table)
assert sorted_table[0, 0] == 102 # Youngest is ID 102 (Age 24)
assert sorted_table[-1, 0] == 104 # Oldest is ID 104 (Age 42)
```

**4. Interview Nuance / Real-World Pitfall:**
Calling `table.sort(axis=0)` will sort Column 0, Column 1, and Column 2 independently, completely dissociating IDs from their corresponding Ages and Salaries! This is a catastrophic data corruption bug.

### Q7: What is `np.lexsort()`, and how does its key tuple ordering convention work?
**1. Definition & Core Concept:**
`np.lexsort(keys)` performs an indirect lexicographical sort using a sequence of keys. Its key ordering convention is **reverse order of precedence**: the **last** key passed in the tuple is the primary sort key, and the **first** key is the secondary/tertiary key.

**2. Technical & Memory Mechanics:**
`lexsort` is modeled after dictionary ordering. In `np.lexsort((secondary_key, primary_key))`:
- Elements are ordered primarily by `primary_key`.
- In the event of a tie in `primary_key`, ties are resolved by `secondary_key`.
`lexsort` employs an internal stable mergesort or radix sort, evaluating keys from right to left (last key to first key).

**3. Explanatory Code Snippet:**
```python
import numpy as np

surnames = np.array(['Smith', 'Jones', 'Smith', 'Adams'])
firstnames = np.array(['John', 'Bob', 'Alice', 'John'])

# Sort primarily by surname, secondarily by firstname
# Pass keys as: (secondary, primary) -> (firstnames, surnames)
idx = np.lexsort((firstnames, surnames))

for i in idx:
    print(f"{surnames[i]}, {firstnames[i]}")
# Output:
# Adams, John
# Jones, Bob
# Smith, Alice  <-- Smith Alice comes before Smith John
# Smith, John
assert surnames[idx[0]] == 'Adams'
assert firstnames[idx[2]] == 'Alice'
```

**4. Interview Nuance / Real-World Pitfall:**
The reversed argument tuple in `lexsort` is universally considered counter-intuitive. 90% of candidates pass `(primary, secondary)` and produce inverted sort orderings. Remember: `lexsort((Z, Y, X))` sorts by $X$, then $Y$, then $Z$.

### Q8: How does `order` parameter work in `np.sort()` when sorting structured arrays?
**1. Definition & Core Concept:**
When sorting a structured array, the `order` parameter accepts a string or list of strings naming the fields to sort by, in order of priority (left-to-right priority).

**2. Technical & Memory Mechanics:**
Unlike `lexsort` which takes `(secondary, primary)`, structured array sorting `arr.sort(order=['primary', 'secondary'])` evaluates fields in standard left-to-right priority order. NumPy compares field byte offsets directly using C comparison functions defined in the `PyArray_Descr` struct.

**3. Explanatory Code Snippet:**
```python
import numpy as np

dtype = [('dept', 'U10'), ('salary', 'i4'), ('id', 'i4')]
employees = np.array([
    ('Engineering', 120000, 1),
    ('Sales', 95000, 2),
    ('Engineering', 90000, 3),
    ('Sales', 110000, 4)
], dtype=dtype)

# Sort primarily by dept, then by salary descending (simulated by negation or separate sort)
sorted_emp = np.sort(employees, order=['dept', 'salary'])

print("Sorted employees:
", sorted_emp)
assert sorted_emp[0]['salary'] == 90000 # Lowest salary in Engineering
assert sorted_emp[1]['salary'] == 120000
```

**4. Interview Nuance / Real-World Pitfall:**
The `order` parameter works ONLY on structured arrays (arrays with named fields in their dtype). Passing `order` to a standard numeric 2D array raises a `ValueError: Cannot sort when the array has no fields`.

### Q9: How can you sort a NumPy array in descending order?
**1. Definition & Core Concept:**
NumPy does not provide a native `ascending=False` argument in `np.sort()`. To sort in descending order, developers either slice the sorted result with negative step `[::-1]` or negate numeric arrays before sorting.

**2. Technical & Memory Mechanics:**
- **Reversed Slicing (`np.sort(a)[::-1]`)**: Slices the ascending sorted copy with step $-1$, creating a zero-copy view with negative stride. Clean, safe, and works for all data types (numbers, strings, booleans).
- **In-Place Sort + Reverse (`a.sort(); a = a[::-1]`)**: Sorts in-place, then creates a reversed view. Note that `a` itself is now a view with negative strides.
- **Negation (`-np.sort(-a)`)**: Negates values before and after sorting. Only works for signed numeric types; fails for unsigned integers, strings, or structured types.

**3. Explanatory Code Snippet:**
```python
import numpy as np

arr = np.array([3, 1, 4, 1, 5, 9, 2])

# Method 1: Sliced view (Universal, Recommended)
desc_view = np.sort(arr)[::-1]
assert np.array_equal(desc_view, [9, 5, 4, 3, 2, 1, 1])

# Method 2: argsort descending
desc_indices = np.argsort(arr)[::-1]
assert np.array_equal(arr[desc_indices], [9, 5, 4, 3, 2, 1, 1])
```

**4. Interview Nuance / Real-World Pitfall:**
Using `-np.sort(-a)` on unsigned integer arrays (like `uint32` or `uint64`) triggers integer underflow wrapping (`-uint(1) == 4294967295`), completely corrupting the sort logic! Always use `[::-1]` slicing for descending sorts.

### Q10: How do `np.partition()` and `ndarray.partition()` differ from full sorting, and what is their computational complexity?
**1. Definition & Core Concept:**
`np.partition(arr, kth)` performs a partial sort using the **Introselect** algorithm. It reorders elements such that the element at the $k$-th position is exactly the element that would be there in a fully sorted array. All elements smaller than the $k$-th element are moved before it, and all larger elements are moved after it, in arbitrary order.

**2. Technical & Memory Mechanics:**
While full sorting requires $O(N \log N)$ comparisons, `partition()` executes in strictly $O(N)$ linear time on average. It operates via recursive Quickselect partitioning, terminating once the $k$-th index is settled. `np.partition()` returns a partitioned copy; `arr.partition()` partitions in-place.

**3. Explanatory Code Snippet:**
```python
import numpy as np

data = np.array([9, 2, 7, 1, 8, 3, 6, 4, 5])

# Find the 3 smallest elements (kth=3)
part = np.partition(data, 3)
print("Partitioned array:", part)
# Element at index 3 is guaranteed to be 4 (the 4th smallest element, 0-indexed)
assert part[3] == 4
# Elements before index 3 are all <= 4 (order arbitrary: e.g. [1, 2, 3])
assert set(part[:3]) == {1, 2, 3}
# Elements after index 3 are all >= 4 (order arbitrary: e.g. [8, 7, 6, 9, 5])
assert all(x >= 4 for x in part[4:])
```

**4. Interview Nuance / Real-World Pitfall:**
When you need only the top-$K$ or bottom-$K$ elements (e.g., top-5 recommendations, median calculation, or anomaly thresholds), calling `np.sort()` is a severe algorithmic anti-pattern ($O(N \log N)$). `np.partition()` finds the top-$K$ in $O(N)$ time.

### Q11: What is `np.argpartition()`, and how is it used to find top-$K$ indices in $O(N)$ time?
**1. Definition & Core Concept:**
`np.argpartition(arr, kth)` performs an indirect partial sort, returning the indices that partition the array. Slicing the first $K$ indices from `argpartition(kth=K)` yields the indices of the $K$ smallest elements in $O(N)$ time.

**2. Technical & Memory Mechanics:**
`argpartition()` returns an integer array where `indices[:k]` point to elements strictly smaller than or equal to `arr[indices[k]]`. The indices themselves are not sorted. If sorted top-$K$ is required, you sort only the $K$-element sub-slice, yielding an overall complexity of $O(N + K \log K)$ instead of $O(N \log N)$.

**3. Explanatory Code Snippet:**
```python
import numpy as np

scores = np.array([55, 92, 34, 88, 72, 99, 12, 60])
K = 3

# Find top-3 highest scores: K largest elements correspond to kth = -3
top_k_idx = np.argpartition(scores, -K)[-K:]

# Slicing gives the indices of [92, 88, 99] (order arbitrary)
print("Top 3 indices (unsorted):", top_k_idx)
assert set(scores[top_k_idx]) == {88, 92, 99}

# Optionally sort only the top K elements
sorted_top_k_idx = top_k_idx[np.argsort(scores[top_k_idx])[::-1]]
print("Top 3 sorted:", scores[sorted_top_k_idx]) # [99, 92, 88]
```

**4. Interview Nuance / Real-World Pitfall:**
For large arrays ($N = 10^7$) where $K = 10$, `argpartition()` executes in ~15 ms, whereas `argsort()` takes ~850 ms—a 55x performance acceleration!

### Q12: How does `np.sort()` handle special floating-point values like `NaN` and `Inf`?
**1. Definition & Core Concept:**
NumPy defines strict sorting semantics for IEEE 754 floating-point values: negative infinity (`-inf`) is sorted first, followed by finite numbers, followed by positive infinity (`+inf`), followed by `NaN` values, which are unconditionally placed at the **very end** of the array.

**2. Technical & Memory Mechanics:**
Standard IEEE 754 specifies that `NaN == NaN` is False and all comparisons involving `NaN` evaluate to False. To maintain strict ordering in C-level sorting without getting stuck in infinite loops, NumPy's sort routines implement special comparison logic (`npy_isnan`): `NaN` is treated as larger than any other value, including `+inf`.

**3. Explanatory Code Snippet:**
```python
import numpy as np

floats = np.array([np.nan, 3.0, -np.inf, np.nan, 0.0, np.inf, -5.0])
sorted_floats = np.sort(floats)

print("Sorted floats:", sorted_floats)
# Output: [-inf, -5.0, 0.0, 3.0, inf, nan, nan]

assert np.isneginf(sorted_floats[0])
assert sorted_floats[1] == -5.0
assert np.isposinf(sorted_floats[-3])
assert np.isnan(sorted_floats[-2])
assert np.isnan(sorted_floats[-1])
```

**4. Interview Nuance / Real-World Pitfall:**
When sorting in descending order using `np.sort(a)[::-1]`, because `NaN` values were at the end of the ascending sort, they now appear at the **very beginning** of the descending array! If downstream code expects the largest finite number at index 0, it will crash or propagate `NaN`.

### Q13: Can you sort an array in-place if it is a non-writeable view?
**1. Definition & Core Concept:**
No. Attempting to call `arr.sort()` on an array or view where `arr.flags.writeable` is `False` immediately raises a `ValueError: assignment destination is read-only`.

**2. Technical & Memory Mechanics:**
At the start of `ndarray.sort()`, NumPy's C function `PyArray_Sort` calls `PyArray_CheckWriteable()`. If the writeable bit in `flags` is cleared (e.g., from `broadcast_to`, memory-mapped read-only files, or explicit locking), the operation aborts before modifying memory. To sort a read-only array, you must use functional `np.sort()`, which allocates an independent writeable copy.

**3. Explanatory Code Snippet:**
```python
import numpy as np

orig = np.array([3, 1, 2])
v = orig.view()
v.flags.writeable = False # Lock view

# In-place sort fails
try:
    v.sort()
except ValueError as e:
    print("Caught expected writeable error:", e)

# Functional sort succeeds (returns new writeable array)
sorted_copy = np.sort(v)
```

### Q14: How does sorting complex numbers (`complex64`, `complex128`) behave in NumPy?
**1. Definition & Core Concept:**
NumPy sorts complex numbers lexicographically by their **real part first**; if real parts are equal, ties are broken by comparing their **imaginary parts**.

**2. Technical & Memory Mechanics:**
The comparison operator in C tests:
$$\text{if } \text{Re}(a) \neq \text{Re}(b) \implies a < b \iff \text{Re}(a) < \text{Re}(b)$$
$$\text{else } \implies a < b \iff \text{Im}(a) < \text{Im}(b)$$
Notice that complex sorting does NOT sort by magnitude (absolute value $|z| = \sqrt{x^2 + y^2}$).

**3. Explanatory Code Snippet:**
```python

# Output: [1. - 5.j, 1.+10.j, 2. + 1.j, 2. + 3.j]

assert sorted_complex[1] == 1 + 10j
assert sorted_complex[2] == 2 + 1j
assert sorted_complex[3] == 2 + 3j
```

**4. Interview Nuance / Real-World Pitfall:**
In physics and digital signal processing, engineers frequently expect complex numbers to sort by magnitude (power/energy). To sort complex numbers by magnitude, you must explicitly use `arr[np.argsort(np.abs(arr))]`.

### Q15: How does boolean array sorting behave?
**1. Definition & Core Concept:**
Sorting a boolean array arranges all `False` values first, followed by all `True` values, because `False` maps numerically to `0` and `True` maps to `1`.

**2. Technical & Memory Mechanics:**
Boolean sort operates as a binary counting sort. In C, it counts the number of `False` (zero) bytes and writes zeroes to the beginning of the buffer and ones to the remainder. Time complexity is $O(N)$ linear time.

**3. Explanatory Code Snippet:**

```python
assert np.array_equal(sorted_bool, [False, False, True, True, True])

# Count falses by indexing

assert sorted_bool[num_false] == True
```

**4. Interview Nuance / Real-World Pitfall:**
While sorting booleans is valid, if your objective is simply to count or partition `True` and `False` values, calling `np.sort()` is redundant. `np.count_nonzero(arr)` or `np.sum(arr)` is orders of magnitude faster.

### Q21: How do memory strides affect CPU cache performance when sorting 2D arrays along `axis=1` versus `axis=0`?
**1. Definition & Core Concept:**
In a standard C-contiguous 2D array, sorting along `axis=1` (rows) operates on memory elements packed consecutively in memory (stride $= \text{itemsize}$). Sorting along `axis=0` (columns) operates on elements separated by large strides (stride $= \text{cols} \times \text{itemsize}$), resulting in poor spatial locality and heavy CPU cache misses.

**2. Technical & Memory Mechanics:**
When sorting along `axis=1`, the CPU hardware prefetcher loads consecutive 64-byte cache lines. A single cache line holds 8 `float64` elements, so 8 comparisons and swaps execute within L1 cache. When sorting along `axis=0`, reading the next element in the same column requires jumping by `cols * 8` bytes. For a $10000 \times 10000$ matrix, each step jumps 80 KB—exceeding L1 cache size! Every comparison triggers an L2/L3 cache miss or DRAM page fetch.

**3. Explanatory Code Snippet:**
```python
import numpy as np
import time

mat = np.random.randn(2000, 2000)

# Benchmark axis=1 (Row-wise sort: contiguous memory)
t0 = time.perf_counter()
np.sort(mat, axis=1)
t_row = time.perf_counter() - t0

# Benchmark axis=0 (Column-wise sort: strided memory)
t0 = time.perf_counter()
np.sort(mat, axis=0)
t_col = time.perf_counter() - t0

print(f"Row sort (contiguous) time: {t_row * 1000:.2f} ms")
print(f"Col sort (strided) time:    {t_col * 1000:.2f} ms")
# Col sort is typically 2x to 5x slower purely due to hardware cache line misses!
```

**4. Interview Nuance / Real-World Pitfall:**
If you need to perform heavy column-wise sorting on a massive C-contiguous matrix, transposing the array (`mat.T`), converting it to a contiguous copy (`np.ascontiguousarray`), sorting rows, and transposing back is often dramatically faster than sorting columns directly!

### Q22: What is the exact memory allocation footprint of `np.sort()` across different algorithms?
**1. Definition & Core Concept:**
`np.sort()` allocates an output copy buffer sized to $N \times \text{itemsize}$ bytes, plus algorithm-specific auxiliary memory during sorting execution.

**2. Technical & Memory Mechanics:**
- `'quicksort'` (Introsort): Allocates $N \times \text{itemsize}$ for the output array. Auxiliary memory: $O(\log N)$ stack frames (~a few kilobytes). Total: $\approx 1.0 \times \text{buffer size}$.
- `'mergesort'` / `'stable'`: Allocates $N \times \text{itemsize}$ for the output array, PLUS an internal temporary merge buffer of size $\lfloor N / 2 \rfloor \times \text{itemsize}$ to execute merge passes. Total peak memory: $\approx 1.5 \times \text{buffer size}$.
- `'heapsort'`: Allocates $N \times \text{itemsize}$ for the output array. Auxiliary memory: $O(1)$ constant bytes. Total: $\approx 1.0 \times \text{buffer size}$.

**3. Explanatory Code Snippet:**
```python
import numpy as np
import tracemalloc

# Trace peak memory allocation during stable sort
tracemalloc.start()
arr = np.random.randn(10_000_000) # 80 MB buffer

# Stable sort requires 80MB output + ~40MB merge buffer = ~120MB peak
sorted_arr = np.sort(arr, kind='stable')
current, peak = tracemalloc.get_traced_memory()
tracemalloc.stop()

print(f"Array buffer size: {arr.nbytes / (1024**2):.1f} MB")
print(f"Peak memory used:  {peak / (1024**2):.1f} MB")
```

**4. Interview Nuance / Real-World Pitfall:**
On memory-constrained systems (e.g. Docker containers with strict cgroup limits), running `kind='stable'` on an array consuming 70% of container RAM will trigger the Linux Out-Of-Memory (OOM) killer due to the auxiliary merge buffer. Use in-place `a.sort(kind='quicksort')` when RAM headroom is tight.

### Q24: What is the internal memory layout of an array during `ndarray.sort()` in-place execution?

```python
assert np.array_equal(arr, [10, 20, 30, 40])
```

### Q25: How does NumPy implement universal SIMD vectorized sorting (AVX-512 / ARM Neon)?

### Q27: How does `np.searchsorted()` leverage pre-sorted memory buffers to achieve $O(\log N)$ search latency?
**1. Definition & Core Concept:**
`np.searchsorted(arr, values, side='left')` uses binary search on a pre-sorted 1D array to find the indices where `values` should be inserted to maintain sorted order, executing in $O(\log N)$ time.

**2. Technical & Memory Mechanics:**
Binary search checks the midpoint index: `mid = (low + high) // 2`. Because the array is sorted, it halves the search range on every step. Hardware prefetchers cannot predict binary search jumps across memory pages, but because it requires only $\approx \log_2(10^6) \approx 20$ memory reads, it executes in sub-microsecond latency.

**3. Explanatory Code Snippet:**
```python
import numpy as np

print(f"Insert {needle} at index: {idx}") # Index 2 (between 20 and 30)

assert idx == 2
# Verify insertion preserves sort
inserted = np.insert(sorted_haystack, idx, needle)
assert np.array_equal(inserted, [10, 20, 25, 30, 40, 50])
```

**4. Interview Nuance / Real-World Pitfall:**
If the input array is NOT sorted, `np.searchsorted` does NOT validate it; it proceeds blindly, returning completely bogus indices without raising any error! You are responsible for ensuring the array is sorted.

### Q28: How does `side='left'` versus `side='right'` differ in `np.searchsorted()` when handling duplicate values?
**1. Definition & Core Concept:**
- `side='left'`: Returns the index of the **first** suitable location (before any existing duplicate elements).
- `side='right'`: Returns the index of the **last** suitable location (after any existing duplicate elements).

**2. Technical & Memory Mechanics:**
Given sorted array `[10, 20, 20, 20, 30]` and search value `20`:
- `side='left'`: Scans until `arr[i-1] < 20 <= arr[i]`, returning index `1`.
- `side='right'`: Scans until `arr[i-1] <= 20 < arr[i]`, returning index `4`.

**3. Explanatory Code Snippet:**
```python
import numpy as np

arr = np.array([10, 20, 20, 20, 30])

idx_left  = np.searchsorted(arr, 20, side='left')
idx_right = np.searchsorted(arr, 20, side='right')

print("Insert 20 (side=left): ", idx_left)  # 1
print("Insert 20 (side=right):", idx_right) # 4

assert idx_left == 1
assert idx_right == 4
# The number of occurrences of 20 is exactly (idx_right - idx_left)
assert (idx_right - idx_left) == 3
```

**4. Interview Nuance / Real-World Pitfall:**
To count occurrences of elements in a sorted array in $O(\log N)$ time, compute `idx_right - idx_left`. This is vastly faster than boolean masking `np.count_nonzero(arr == val)` ($O(N)$).

### Q30: How does indirect multi-column sorting via `np.lexsort()` navigate strided 2D column slices?
**1. Definition & Core Concept:**

```python
", sorted_mat)
# [[ 1, 40],
#  [ 1, 90],
#  [ 2, 10],
#  [ 2, 50]]

assert sorted_mat[1, 0] == 1 and sorted_mat[1, 1] == 90
```

### Q31: What is the computational complexity and memory behavior of `np.partition()` compared to `np.sort()`?
**1. Definition & Core Concept:**
`np.partition()` implements the **Introselect** algorithm, which achieves $O(N)$ linear time complexity on average and in the worst case, whereas `np.sort()` achieves $O(N \log N)$.

**2. Technical & Memory Mechanics:**
QuickSort partitions both halves of the array recursively:
$$T(N) = 2 T(N/2) + O(N) = O(N \log N)$$
Introselect partitions only the single sub-array that contains the target $k$-th index:
$$T(N) = T(N/2) + O(N) = O(N)$$
Peak memory: `np.partition` allocates an $O(N)$ output array copy; `a.partition()` operates in-place using $O(1)$ auxiliary memory.

**3. Explanatory Code Snippet:**
```python
import numpy as np
import time

# 1. Full Sort: O(N log N)
t0 = time.perf_counter()
s = np.sort(big_data)
t_sort = time.perf_counter() - t0

# 2. Partition: O(N)
t0 = time.perf_counter()
p = np.partition(big_data, 10)
t_part = time.perf_counter() - t0

print(f"Full Sort time: {t_sort * 1000:.2f} ms")
print(f"Partition time: {t_part * 1000:.2f} ms")
print(f"Speedup:        {t_sort / t_part:.1f}x")
# Partition is typically 5x to 15x faster on large arrays!
```

**4. Interview Nuance / Real-World Pitfall:**
Candidates often assume `np.partition(arr, [k1, k2])` can only take a single integer. In fact, `kth` can be a list or tuple of multiple indices! `np.partition(arr, (10, 100))` partitions multiple split points simultaneously in $O(N)$ time.

**4. Interview Nuance / Real-World Pitfall:**
If you pass `records['age'].sort()`, you sort the `age` field view independently, scrambling ages across individuals while leaving names and weights untouched! Always call `records.sort(order='age')`.

### Q33: How does `order` handle nested structured arrays?
**1. Definition & Core Concept:**
When structured arrays contain nested record definitions, the `order` parameter can specify nested field names using tuple notation: `order=[('parent_field', 'child_field')]`.

**2. Technical & Memory Mechanics:**
NumPy navigates the nested struct's descriptor tree, accumulating byte offsets: $\text{total\_offset} = \text{offset}_{\text{parent}} + \text{offset}_{\text{child}}$.

**3. Explanatory Code Snippet:**

```python
import numpy as np

nested_dt = np.dtype([

arr = np.array([

sorted_arr = np.sort(arr, order=[('info', 'age')])
assert sorted_arr[0]['info']['name'] == 'Charlie'
assert sorted_arr[1]['info']['name'] == 'Bob'
```

**4. Interview Nuance / Real-World Pitfall:**
String path notation like `'info.age'` is NOT supported in NumPy's `order` argument; you must pass nested tuples `('info', 'age')`.

### Q34: What is the time complexity of sorting an array that is already 100% pre-sorted under different algorithms?
**1. Definition & Core Concept:**
Under `'quicksort'` (Introsort), pre-sorted arrays take $O(N \log N)$ time (median-of-three pivot prevents worst-case $O(N^2)$). Under `'mergesort'` / `'stable'` (Timsort), pre-sorted arrays execute in strictly **$O(N)$ linear time**.

**2. Technical & Memory Mechanics:**
Timsort iterates through the array detecting contiguous ascending runs. If the entire array is a single ascending run, Timsort performs $N - 1$ comparisons and terminates with 0 merges! QuickSort, even with median-of-three, must still recursively divide and partition the sub-arrays.

**3. Explanatory Code Snippet:**
```python
import numpy as np
import time

sorted_data = np.arange(1_000_000, dtype=np.float64)

# 1. QuickSort on pre-sorted array: O(N log N)
t0 = time.perf_counter()
np.sort(sorted_data, kind='quicksort')
t_quick = time.perf_counter() - t0

# 2. Stable/Timsort on pre-sorted array: O(N)
t0 = time.perf_counter()
np.sort(sorted_data, kind='stable')
t_stable = time.perf_counter() - t0

print(f"QuickSort on presorted:  {t_quick * 1000:.2f} ms")
print(f"Timsort on presorted:    {t_stable * 1000:.2f} ms")
# Timsort is significantly faster on presorted data!
```

**4. Interview Nuance / Real-World Pitfall:**
If you know your data is partially or mostly pre-sorted (e.g. streaming time-series log timestamps), specifying `kind='stable'` provides substantial speedups over the default quicksort.

### Q35: How do memory alignment and itemsize impact sorting speed?
**1. Definition & Core Concept:**
Unaligned data or unusual itemsizes disable hardware SIMD vector loads, forcing the sorting engine to fall back to scalar byte-copy routines.

**2. Technical & Memory Mechanics:**
64-bit integers and floats aligned to 8-byte boundaries allow direct CPU register loads (`mov [rax], rbx`). If an array view starts at an unaligned byte address (e.g., from raw byte slicing), every comparison requires unaligned memory access, and SIMD sorting networks cannot engage.

**3. Explanatory Code Snippet:**
```python
import numpy as np

# 1. Aligned array
aligned = np.random.randn(100000)
assert aligned.flags.aligned is True

# 2. Unaligned view (offset by 1 byte)
raw_bytes = np.zeros(aligned.nbytes + 1, dtype=np.uint8)
unaligned = raw_bytes[1:aligned.nbytes+1].view(np.float64)
assert unaligned.flags.aligned is False
```

**4. Interview Nuance / Real-World Pitfall:**
Always ensure arrays are aligned (`np.require(arr, requirements=['A'])`) before passing them to performance-sensitive sorting routines.

### Q36: How does `np.sort()` perform on boolean-masked subsets versus in-place masked assignment?
**1. Definition & Core Concept:**
Calling `np.sort(arr[mask])` sorts only the extracted copy. To sort elements matching a mask and write them back to their original positions in the parent array, you must reassign via fancy indexing: `arr[mask] = np.sort(arr[mask])`.

**2. Technical & Memory Mechanics:**
`arr[mask]` returns an independent heap copy. Calling `np.sort(arr[mask])` sorts that copy. The parent array `arr` is untouched until the sorted values are written back into `arr[mask]`.

**3. Explanatory Code Snippet:**
```python
import numpy as np

arr = np.array([10, -5, 20, -1, 30, -8])
mask = arr < 0 # Negatives: [-5, -1, -8]

# Sort ONLY negative numbers in-place in the array
arr[mask] = np.sort(arr[mask])

print("Array with sorted negatives:", arr)
# Negatives [-8, -5, -1] occupy the original negative positions!
assert arr[1] == -8
assert arr[3] == -5
assert arr[5] == -1
```

**4. Interview Nuance / Real-World Pitfall:**
Writing `arr[mask].sort()` fails silently to update `arr`! Because `arr[mask]` produces a temporary copy, `arr[mask].sort()` mutates the temporary copy and discards it.

### Q37: How does `np.argsort()` handle multidimensional arrays when `axis=None`?
**1. Definition & Core Concept:**
Unlike `np.sort(arr, axis=None)` which returns a 1D sorted array, `np.argsort(arr, axis=None)` flattens the array, sorts it, and returns the 1D flat indices into the flattened array.

**2. Technical & Memory Mechanics:**
To convert the 1D flat indices back into multi-dimensional coordinate tuples, you must use `np.unravel_index(flat_indices, arr.shape)`.

**3. Explanatory Code Snippet:**
```python
import numpy as np

mat = np.array([
    [9, 2],
    [5, 1]
])

flat_idx = np.argsort(mat, axis=None)
print("Flat argsort indices:", flat_idx) # [3, 1, 2, 0] (values: 1, 2, 5, 9)

# Convert flat indices to 2D row/col coordinates
row_coords, col_coords = np.unravel_index(flat_idx, mat.shape)
print("2D coordinates:")
for r, c in zip(row_coords, col_coords):
    print(f"  mat[{r}, {c}] = {mat[r, c]}")

assert mat[row_coords[0], col_coords[0]] == 1 # Minimum
assert mat[row_coords[-1], col_coords[-1]] == 9 # Maximum
```

**4. Interview Nuance / Real-World Pitfall:**
Passing 1D indices directly into a 2D matrix (`mat[flat_idx]`) indexes along axis 0, which raises an `IndexError: index out of bounds` or produces incorrect slicing. Always use `np.unravel_index`.

### Q38: How does `take_along_axis()` simplify multidimensional indirect sorting compared to manual indexing?
**1. Definition & Core Concept:**
`np.take_along_axis(arr, indices, axis)` extracts values along the specified axis using index arrays generated by `np.argsort()`, eliminating complex multidimensional meshgrid indexing.

**2. Technical & Memory Mechanics:**
When `argsort(mat, axis=1)` produces a 2D index matrix of shape $(M, N)$, you cannot write `mat[:, indices]`. In standard NumPy fancy indexing, that triggers broadcast indexing. `take_along_axis` iterates over slice indices along `axis`, mapping `out[i, j] = arr[i, indices[i, j]]`.

**3. Explanatory Code Snippet:**
```python
import numpy as np

mat = np.array([
    [90, 10, 50],
    [20, 80, 40]
])

# Sort each row independently via argsort
sort_idx = np.argsort(mat, axis=1)

# Correct extraction of sorted values using take_along_axis
sorted_mat = np.take_along_axis(mat, sort_idx, axis=1)

print("Sorted via take_along_axis:
", sorted_mat)
assert np.array_equal(sorted_mat, np.sort(mat, axis=1))
```

**4. Interview Nuance / Real-World Pitfall:**
`take_along_axis()` was introduced in NumPy 1.15 specifically to eliminate the nightmare of writing `np.ogrid` or `np.ix_` boilerplate when applying multidimensional `argsort` results.

### Q39: What is `put_along_axis()`, and how is it used to scatter sorted values back into multidimensional arrays?
**1. Definition & Core Concept:**
`np.put_along_axis(arr, indices, values, axis)` is the complement of `take_along_axis()`. It scatters `values` into `arr` at the positions specified by `indices` along `axis` in-place.

**2. Technical & Memory Mechanics:**
For 2D array along `axis=1`, it executes `arr[i, indices[i, j]] = values[i, j]`. It mutates `arr` in-place without generating intermediate full-sized index grids.

**3. Explanatory Code Snippet:**
```python
import numpy as np

arr = np.zeros((2, 3), dtype=np.int32)
# Specify where to place values along axis 1
indices = np.array([[2, 0], [1, 2]])
values = np.array([[99, 11], [55, 77]])

np.put_along_axis(arr, indices, values, axis=1)
print("Array after put_along_axis:
", arr)

assert arr[0, 2] == 99
assert arr[0, 0] == 11
assert arr[1, 1] == 55
assert arr[1, 2] == 77
```

**4. Interview Nuance / Real-World Pitfall:**
If duplicate indices exist in `indices` along the same slice, the write order is non-deterministic, and the final value in that slot depends on internal iteration order.

### Q40: How does `np.sort()` interact with object arrays (`dtype=object`)?
**1. Definition & Core Concept:**
When sorting an array of `dtype=object`, NumPy falls back to Python-level comparison by calling `PyObject_RichCompareBool` (`<` operator) on every pair of elements.

**2. Technical & Memory Mechanics:**
Because elements in an object array are pointers to arbitrary Python objects on the heap:
- Every comparison invokes Python interpreter overhead and acquires the GIL.
- If objects cannot be compared (e.g. comparing an integer with a dictionary), Python raises `TypeError: '<' not supported between instances`.
- Sorting is significantly slower (10x to 50x) than primitive numeric sorting.

**3. Explanatory Code Snippet:**
```python
import numpy as np

# Object array with comparable custom objects
class PriorityItem:
    def __init__(self, priority: int, name: str):
        self.priority = priority
        self.name = name
    def __lt__(self, other):
        return self.priority < other.priority
    def __repr__(self):
        return f"{self.name}({self.priority})"

items = np.array([PriorityItem(3, 'Low'), PriorityItem(1, 'High'), PriorityItem(2, 'Med')], dtype=object)
items.sort()

print("Sorted object array:", items)
assert items[0].name == 'High'
assert items[-1].name == 'Low'
```

**4. Interview Nuance / Real-World Pitfall:**
If an object array contains `None` mixed with numbers, calling `.sort()` raises a `TypeError` in Python 3 because `None < 5` is undefined.

### Q41: What are the trade-offs between `np.sort()` (copy) and `arr.sort()` (in-place) in production systems?
**1. Definition & Core Concept:**
`np.sort()` prioritizes functional purity and data immutability by allocating a new array, while `arr.sort()` prioritizes memory efficiency and execution speed by modifying the buffer in-place.

**2. Technical & Memory Mechanics:**
- `np.sort()`: Allocates $N \times \text{itemsize}$ bytes. Protects caller data from side-effects, making it safe for multi-threaded pipelines or when the original array must remain unsorted. Space: $O(N)$.
- `arr.sort()`: Operates directly on the existing pointer `arr->data`. Allocates zero buffer bytes. Mutates the original array and any shared views. Up to 2x faster because it avoids allocation and memory copying. Space: $O(1)$ auxiliary (for quicksort).

**3. Explanatory Code Snippet:**
```python
import numpy as np

# Safe Functional Pattern:
def compute_quantiles_safe(raw_features: np.ndarray):
    # Does not mutate raw_features in caller's scope
    sorted_copy = np.sort(raw_features)
    return sorted_copy[len(sorted_copy) // 2]

# High-Performance In-Place Pattern:
def compute_quantiles_fast(scratchpad: np.ndarray):
    # Mutates scratchpad in-place (assumes scratchpad is disposable)
    scratchpad.sort()
    return scratchpad[len(scratchpad) // 2]

data = np.array([5, 2, 8, 1])
compute_quantiles_safe(data)
assert np.array_equal(data, [5, 2, 8, 1]) # Preserved!

compute_quantiles_fast(data)
assert np.array_equal(data, [1, 2, 5, 8]) # Mutated!
```

**4. Interview Nuance / Real-World Pitfall:**
In microservices handling high concurrency, using `arr.sort()` on shared or cached arrays causes data race conditions and corrupts upstream analytics. Use `arr.sort()` only on dedicated thread-local scratchpads.

### Q42: When should an engineer use `np.argsort()` instead of `np.sort()`?
**1. Definition & Core Concept:**
Use `np.argsort()` whenever you need to sort multiple associated arrays synchronously, extract rank positions, or reorder multidimensional tables based on a key column. Use `np.sort()` when you only care about the sorted values of a single array.

**2. Technical & Memory Mechanics:**
`np.sort()` loses the original index mappings of elements. Once sorted, you cannot determine where element $x$ originated. `np.argsort()` produces an index permutation array $P$. Applying $P$ to other aligned arrays (e.g., timestamps, labels, IDs) reorders all correlated datasets into matching order.

**3. Explanatory Code Snippet:**
```python
import numpy as np

timestamps = np.array([1050, 1010, 1040, 1020])
sensor_ids = np.array(['S3', 'S1', 'S4', 'S2'])
voltages   = np.array([3.3, 3.1, 3.4, 3.2])

# Sort all arrays by timestamp synchronously
sort_p = np.argsort(timestamps)

sorted_timestamps = timestamps[sort_p]
sorted_sensor_ids = sensor_ids[sort_p]
sorted_voltages   = voltages[sort_p]

print("Chronological Sensors:  ", sorted_sensor_ids) # ['S1', 'S2', 'S4', 'S3']
print("Chronological Voltages: ", sorted_voltages)   # [3.1, 3.2, 3.4, 3.3]

assert sorted_sensor_ids[0] == 'S1'
```

**4. Interview Nuance / Real-World Pitfall:**
`np.argsort()` incurs an extra memory allocation (8 bytes per element for `intp` indices) plus the latency of subsequent fancy indexing. If you only need sorted values of a single array, `np.sort()` is 2x to 3x faster.

### Q43: How do QuickSort, MergeSort/Stable, and HeapSort compare in runtime, memory, and stability?
**1. Definition & Core Concept:**
NumPy provides three classical algorithmic families, each with distinct trade-offs between average runtime, worst-case guarantees, auxiliary memory, and stability.

**2. Technical & Memory Mechanics:**
- **Introsort (`quicksort`)**: Average $O(N \log N)$, worst-case $O(N \log N)$ via heapsort fallback. Auxiliary memory: $O(\log N)$. **Unstable**. Best cache locality. Default choice for speed.
- **Timsort (`mergesort` / `stable`)**: Average $O(N \log N)$, worst-case $O(N \log N)$, best-case $O(N)$ on presorted data. Auxiliary memory: $O(N/2)$ to $O(N)$. **Stable**. Best when relative order of equal keys must be preserved.
- **HeapSort (`heapsort`)**: Worst-case $O(N \log N)$ strictly guaranteed. Auxiliary memory: $O(1)$. **Unstable**. Poor cache locality; 2x to 3x slower in practice than quicksort. Best for hard real-time systems where $O(1)$ memory guarantees are required.

**3. Explanatory Code Snippet:**
```python
import numpy as np

# Comparative Benchmark Demo
arr = np.random.randn(1_000_000)

s_quick = np.sort(arr, kind='quicksort') # Fastest general sort
s_merge = np.sort(arr, kind='stable')    # Stable, O(N) memory
s_heap  = np.sort(arr, kind='heapsort')  # O(1) memory, slowest cache
```

**4. Interview Nuance / Real-World Pitfall:**
QuickSort in NumPy is actually **Introsort**. It does NOT suffer from the classical QuickSort worst-case $O(N^2)$ degradation on sorted or reverse-sorted data because it monitors recursion depth and falls back to HeapSort.

### Q44: Why is `np.partition()` vastly superior to `np.sort()` for $K$-Nearest Neighbors (KNN) and Top-$K$ selection?
**1. Definition & Core Concept:**
Finding the $K$ smallest or largest elements in an array does not require sorting all $N$ elements. `np.partition()` executes in $O(N)$ linear time using Introselect, whereas `np.sort()` burns $O(N \log N)$ operations.

**2. Technical & Memory Mechanics:**
In KNN, you compute distances from a query point to $10^6$ dataset points. You only need the $K=10$ nearest neighbors.
- Full sort: Compares and orders all $10^6$ elements ($10^6 \times 20 \approx 2 \times 10^7$ operations).
- Partition: Divides the array around the 10th element in $\approx 2 \times 10^6$ operations. Slicing `distances[np.argpartition(distances, 10)[:10]]` delivers the 10 nearest points up to 10x faster.

**3. Explanatory Code Snippet:**
```python
import numpy as np
import time

distances = np.random.uniform(0, 1000, 1_000_000)
K = 5

# Anti-pattern: Full argsort
t0 = time.perf_counter()
knn_full = np.argsort(distances)[:K]
t_full = time.perf_counter() - t0

# Production pattern: argpartition
t0 = time.perf_counter()
knn_part = np.argpartition(distances, K)[:K]
knn_part_sorted = knn_part[np.argsort(distances[knn_part])]
t_part = time.perf_counter() - t0

print(f"Full argsort KNN time: {t_full * 1000:.2f} ms")
print(f"argpartition KNN time: {t_part * 1000:.2f} ms")
print(f"Speedup:               {t_full / t_part:.1f}x")

assert np.allclose(distances[knn_full], distances[knn_part_sorted])
```

**4. Interview Nuance / Real-World Pitfall:**
In production recommender systems or vector databases, failing to use `argpartition` for top-$K$ candidate retrieval is one of the most common CPU bottlenecks.

### Q45: How does `np.lexsort()` compare with sorting structured arrays using `order`?
**1. Definition & Core Concept:**
`np.lexsort()` performs indirect multi-key sorting across separate 1D arrays and uses reverse-order tuple syntax. Structured array sorting operates on a single array of structured records using standard forward-order field names.

**2. Technical & Memory Mechanics:**
- `np.lexsort((k3, k2, k1))`: Operates on independent columnar arrays. Returns an index permutation array. Ideal when data is already stored as columnar NumPy arrays or when you do not want to allocate a structured array.
- `np.sort(struct_arr, order=['k1', 'k2', 'k3'])`: Operates on row-based structured records in-place or out-of-place. Reorders the full composite records directly.

**3. Explanatory Code Snippet:**
```python
import numpy as np

# Columnar data
names = np.array(['Alice', 'Bob', 'Alice', 'Bob'])

# Lexsort: Sort by name, then by score
idx = np.lexsort((scores, names)) # (secondary, primary)
print("Lexsorted indices:", idx)

# Structured Array equivalent
records = np.array(list(zip(names, scores)), dtype=[('name', 'U10'), ('score', 'i4')])
sorted_records = np.sort(records, order=['name', 'score'])
assert sorted_records['score'][0] == 85
assert sorted_records['score'][1] == 95
```

**4. Interview Nuance / Real-World Pitfall:**
`lexsort` is always stable (using mergesort/radix sort). Structured sorting with `order` defaults to quicksort (unstable) unless `kind='stable'` is explicitly passed.

### Q46: What are the cache implications of sorting along rows (`axis=1`) versus sorting along columns (`axis=0`)?
**1. Definition & Core Concept:**
In C-contiguous arrays, sorting rows (`axis=1`) reads contiguous memory addresses, maximizing L1 cache line hits. Sorting columns (`axis=0`) reads strided memory addresses, forcing constant CPU cache line evictions.

**2. Technical & Memory Mechanics:**
When sorting along `axis=1`, adjacent elements are 8 bytes apart. Each 64-byte L1 cache line load brings in 8 elements. When sorting along `axis=0` in a $5000 \times 5000$ matrix, adjacent column elements are 40,000 bytes apart! Every comparison accesses a completely new cache line, stalling the CPU instruction pipeline waiting for DRAM page retrieval.

**3. Explanatory Code Snippet:**
```python
import numpy as np
import time

A = np.random.randn(4000, 4000)

t0 = time.perf_counter()
np.sort(A, axis=1) # Contiguous row sort
t_row = time.perf_counter() - t0

t0 = time.perf_counter()
np.sort(A, axis=0) # Strided column sort
t_col = time.perf_counter() - t0

print(f"Row sort: {t_row * 1000:.2f} ms | Col sort: {t_col * 1000:.2f} ms")
```

**4. Interview Nuance / Real-World Pitfall:**
If an algorithm must sort along columns, transposing the array (`A.T`), converting it to C-contiguous layout (`np.ascontiguousarray`), sorting rows, and transposing back is often up to 3x faster than sorting columns directly.

### Q47: How does `take_along_axis()` compare to manual fancy indexing when applying `argsort()` results?
**1. Definition & Core Concept:**
`np.take_along_axis()` maps 2D/ND `argsort` results directly along the sort axis without manual index meshgrid construction. Manual fancy indexing requires constructing full index grids using `np.ogrid` or `np.ix_`.

**2. Technical & Memory Mechanics:**
For a 2D matrix of shape $(M, N)$, `idx = np.argsort(mat, axis=1)` has shape $(M, N)$. If you write `mat[np.arange(M)[:, None], idx]`, you must manually broadcast row indices against `idx`. `take_along_axis(mat, idx, axis=1)` encapsulates this C-level traversal cleanly and with zero Python meshgrid overhead.

**3. Explanatory Code Snippet:**
```python
import numpy as np

mat = np.array([
    [30, 10, 20],
    [60, 40, 50]
])

idx = np.argsort(mat, axis=1)

# Method 1: Modern clean take_along_axis
res1 = np.take_along_axis(mat, idx, axis=1)

# Method 2: Legacy manual meshgrid fancy indexing
rows = np.arange(mat.shape[0])[:, None]
res2 = mat[rows, idx]

assert np.array_equal(res1, res2)
assert np.array_equal(res1, np.sort(mat, axis=1))
```

**4. Interview Nuance / Real-World Pitfall:**
Writing `mat[:, idx]` is a fatal bug! It attempts 3D tensor broadcasting, resulting in shape `(2, 2, 3)` rather than sorting the matrix! Always use `take_along_axis`.

### Q48: How do in-place sorting on views and copying before sorting differ in multi-threaded Python programs?
**1. Definition & Core Concept:**
In multi-threaded programs where NumPy releases the GIL, calling `view.sort()` in-place modifies the parent array's buffer, creating severe race conditions if other threads are reading. Allocating a copy (`np.sort(view)`) ensures thread-local data isolation.

**2. Technical & Memory Mechanics:**
Because NumPy releases the GIL during `ndarray.sort()`, two worker threads sorting overlapping views of the same array will execute C-level memory swaps simultaneously on the same physical memory addresses, causing memory corruption or segmentation faults.

**3. Explanatory Code Snippet:**
```python
import numpy as np

# Unsafe multi-threaded pattern (Shared Buffer)
shared_buffer = np.random.randn(1000)
v1 = shared_buffer[:600]
v2 = shared_buffer[400:] # Overlapping range 400..600!
# v1.sort() and v2.sort() in parallel threads will corrupt memory!

# Safe multi-threaded pattern:
# Thread 1:
sorted_1 = np.sort(v1) # Isolated copy
# Thread 2:
sorted_2 = np.sort(v2) # Isolated copy
```

**4. Interview Nuance / Real-World Pitfall:**
When dispatching array slices to `ThreadPoolExecutor`, never call `.sort()` on the incoming slices unless you have proven they are non-overlapping and caller data mutation is intended.

### Q49: How do Python's built-in `sorted()` / `list.sort()` compare with NumPy's `np.sort()` / `ndarray.sort()`?
**1. Definition & Core Concept:**
Python's built-in sorting operates on heterogeneous Python object pointers using pure Timsort. NumPy's sorting operates on contiguous C-level primitive memory buffers using Introsort, SIMD vectorization, and specialized C comparisons.

**2. Technical & Memory Mechanics:**
- Python `list.sort()`: Dereferences a pointer for every element, extracts Python `PyObject` structs, executes Python dynamic type lookups, and swaps 64-bit pointers. Highly expressive but high overhead.

**4. Interview Nuance / Real-World Pitfall:**

### Q50: How does Pandas `sort_values()` interact with underlying NumPy sorting routines?
**1. Definition & Core Concept:**
Pandas `DataFrame.sort_values(by='col')` uses NumPy's `np.lexsort()` or `np.argsort(kind='mergesort')` under the hood to calculate row permutation indices, and then reindexes its internal BlockManager columns.

**2. Technical & Memory Mechanics:**
When sorting a DataFrame by multiple columns:
1. Pandas extracts the underlying 1D NumPy arrays for each column.
2. It passes them to `np.lexsort(keys[::-1])` or an internal radix sorter.
3. It takes the resulting `intp` index vector and calls `take()` on every column block.
4. It attaches the reordered index to a new DataFrame.

**3. Explanatory Code Snippet:**
```python
import numpy as np
import pandas as pd

df = pd.DataFrame({
    'cat': ['B', 'A', 'B', 'A'],
    'val': [10, 20, 5, 15]
})

# Pandas sort
df_sorted = df.sort_values(by=['cat', 'val'])

# Pure NumPy equivalent under the hood
keys = (df['val'].values, df['cat'].values) # (secondary, primary)
idx = np.lexsort(keys)
numpy_sorted_df = df.iloc[idx]

assert np.array_equal(df_sorted.values, numpy_sorted_df.values)
```

**4. Interview Nuance / Real-World Pitfall:**

### Q51: What is the "Descending NaN Trap" when sorting arrays containing `NaN` values?
**1. Definition & Core Concept:**
In ascending order, NumPy unconditionally sorts `NaN` to the end. When reversing the sorted array to achieve descending order (`np.sort(a)[::-1]`), `NaN` values are flipped to the **beginning** of the array, breaking downstream numerical calculations!

**2. Technical & Memory Mechanics:**
NumPy defines `NaN` as greater than any finite number or `+inf`. In ascending sort: `[-5, 0, 10, nan]`. When reversed with `[::-1]`: `[nan, 10, 0, -5]`. The first element is now `NaN`! Any downstream algorithm expecting the maximum value at index 0 receives `NaN`.

**3. Explanatory Code Snippet:**
```python
import numpy as np

data = np.array([10.0, np.nan, 50.0, 20.0, np.nan])

# NAIVE DESCENDING SORT: NaN trap!
naive_desc = np.sort(data)[::-1]
print("Naive descending:", naive_desc)
# [nan, nan, 50., 20., 10.] -> NaNs are at the front!

# ROBUST DESCENDING SORT: Keep NaNs at the end
nan_mask = np.isnan(data)
valid_sorted = np.sort(data[~nan_mask])[::-1]
robust_desc = np.empty_like(data)
robust_desc[:len(valid_sorted)] = valid_sorted
robust_desc[len(valid_sorted):] = np.nan

print("Robust descending:", robust_desc)
# [50., 20., 10., nan, nan] -> Max finite value is correctly at index 0!
assert robust_desc[0] == 50.0
assert np.isnan(robust_desc[-1])
```

**4. Interview Nuance / Real-World Pitfall:**
This is one of the most common silent bugs in quantitative finance backtesters. Sorting stock returns descending brings `NaN` (untraded stocks) to the top of the portfolio, allocating capital to `NaN` positions!

### Q52: Why does negating unsigned integer arrays (`-arr`) to achieve descending sort fail catastrophically?
**1. Definition & Core Concept:**
Unsigned integers (`uint8`, `uint16`, `uint32`, `uint64`) cannot represent negative numbers. Negating an unsigned integer triggers modular arithmetic underflow, converting small numbers into massive numbers!

**2. Technical & Memory Mechanics:**
In `uint8`, value `1` negated becomes `-1 \pmod{256} = 255`. Value `250` negated becomes `-250 \pmod{256} = 6`. Sorting `-arr` completely scrambles the order of elements rather than reversing them.

**3. Explanatory Code Snippet:**
```python

neg_u = -u_arr
print("Negated uint8 values:", neg_u) # [255, 246, 6]
wrong_sort = np.sort(-u_arr)
print("Sorted negated:       ", wrong_sort) # [6, 246, 255]

# CORRECT: Slice with negative step
correct_desc = np.sort(u_arr)[::-1]
print("Correct descending:   ", correct_desc) # [250, 10, 1]
assert np.array_equal(correct_desc, [250, 10, 1])
```

**4. Interview Nuance / Real-World Pitfall:**
In modern NumPy, applying the unary negation operator `-` to unsigned integers raises a `TypeError` or `DeprecationWarning: Bitwise inversion '~' or explicit subtraction should be used`. Never use negation for descending sorts.

### Q55: What happens if you attempt to sort an array created via `np.broadcast_to()`?
**1. Definition & Core Concept:**
Attempting to sort a broadcasted array in-place via `arr.sort()` raises `ValueError: cannot set WRITEABLE flag to True of array with zero strides` or `ValueError: assignment destination is read-only`.

**2. Technical & Memory Mechanics:**
`np.broadcast_to()` sets strides to 0 along broadcasted axes and marks the array read-only. Sorting in-place requires swapping memory bytes. If multiple logical elements map to the exact same physical byte (zero stride), in-place sorting would cause memory corruption. Functional `np.sort()` succeeds because it creates a new, independent contiguous copy before sorting.

**3. Explanatory Code Snippet:**

```python
# In-place sort fails:
try:
    b.sort(axis=-1)
except ValueError as e:
    print("Caught expected broadcast sort error:", e)

# Functional sort succeeds:

assert sorted_b.shape == (4, 3)
assert np.array_equal(sorted_b[0], [1, 2, 3])
```

**4. Interview Nuance / Real-World Pitfall:**
Broadcasted arrays are strictly read-only views. If you need to manipulate or sort them, you must allocate a contiguous copy first (`b.copy()`) or use functional `np.sort(b)`.

### Q56: How do high-frequency trading (HFT) matching engines maintain sorted Level-2 order books with sub-microsecond latency?
**1. Definition & Core Concept:**
Matching engines process thousands of bid/ask limit orders per second. Maintaining sorted price levels must be done in-place without dynamic memory allocation or full $O(N \log N)$ sorts on every tick.

**2. Technical & Memory Mechanics:**
The engine pre-allocates a fixed array of shape `(MAX_DEPTH, 2)` (Price, Size). When a new limit order arrives:
- It uses `np.searchsorted()` to find the insertion index in $O(\log N)$ time.
- If the price level exists, it updates volume in-place.
- If it is a new price level, it shifts lower levels down using `np.copyto` and inserts the new order in $O(K)$ time.
- Total latency: ~200 nanoseconds; zero heap allocations.

**3. Explanatory Code Snippet:**
```python
import numpy as np

class FastOrderBookBids:
    def __init__(self, max_depth: int = 10):
        self.prices = np.zeros(max_depth, dtype=np.float64)
        self.sizes = np.zeros(max_depth, dtype=np.float64)
        self.count = 0

    def insert_bid(self, price: float, size: float):
        # Bids are sorted DESCENDING. To use searchsorted, search in negative prices:
        # Or search in ascending and invert.
        # Find position using binary search:
        active_prices = -self.prices[:self.count]
        idx = np.searchsorted(active_prices, -price)
        
        # Shift down and insert
        if self.count < len(self.prices):
            self.prices[idx+1:self.count+1] = self.prices[idx:self.count]
            self.sizes[idx+1:self.count+1] = self.sizes[idx:self.count]
            self.count += 1
        else:
            self.prices[idx+1:] = self.prices[idx:-1]
            self.sizes[idx+1:] = self.sizes[idx:-1]
        
        self.prices[idx] = price
        self.sizes[idx] = size

book = FastOrderBookBids(5)
book.insert_bid(100.5, 10)
book.insert_bid(101.0, 50) # Higher bid -> Should be index 0
book.insert_bid(99.0, 30)  # Lower bid -> Should be last

assert book.prices[0] == 101.0
assert book.prices[1] == 100.5
assert book.prices[2] == 99.0
```

**4. Interview Nuance / Real-World Pitfall:**
Calling `np.sort()` on every incoming tick is an immediate disqualifier in quantitative developer interviews. Insertion into pre-sorted arrays via `searchsorted` is the gold standard.

### Q57: How do deep learning classification pipelines extract Top-$K$ class predictions efficiently?
**1. Definition & Core Concept:**
ImageNet models output probability logits across 1,000 classes. For real-time inference (e.g. 60 FPS video), sorting all 1,000 logits per frame wastes CPU cycles. `np.argpartition` extracts the Top-5 predictions in $O(C)$ time.

**2. Technical & Memory Mechanics:**
For $C=1000$ classes and batch size $B=64$:
- Full sort: $64 \times 1000 \log_2(1000) \approx 6.4 \times 10^5$ operations.
- `argpartition(..., -5)`: $64 \times 1000 \approx 6.4 \times 10^4$ operations (10x reduction).
- After partitioning, sort only the 5 selected items: $5 \log_2(5) \approx 12$ operations.

**3. Explanatory Code Snippet:**
```python

logits = np.random.randn(64, 1000)
K = 5

# Fast Top-K extraction
# Partition the top K indices along axis 1
top_k_unsorted = np.argpartition(logits, -K, axis=1)[:, -K:]

# Extract the values of the top K
top_k_values = np.take_along_axis(logits, top_k_unsorted, axis=1)

# Sort only the K values
sorted_within_top_k = np.argsort(top_k_values, axis=1)[:, ::-1]
final_top_k_indices = np.take_along_axis(top_k_unsorted, sorted_within_top_k, axis=1)

assert final_top_k_indices.shape == (64, 5)
```

**4. Interview Nuance / Real-World Pitfall:**

### Q58: In computer vision object detection, how is bounding box Non-Maximum Suppression (NMS) accelerated using `argsort()`?
**1. Definition & Core Concept:**
NMS filters overlapping bounding boxes based on detection confidence scores. Bounding boxes must be processed in descending order of confidence score.

**2. Technical & Memory Mechanics:**
1. Sort detection confidence scores descending using `order = scores.argsort()[::-1]`.
2. Select the top candidate box `order[0]`.
3. Compute Intersection-over-Union (IoU) between box 0 and all remaining boxes in `order[1:]`.
4. Discard all boxes with $\text{IoU} > \text{threshold}$.
5. Repeat for remaining candidates.

**3. Explanatory Code Snippet:**
```python
import numpy as np

def nms_fast(boxes: np.ndarray, scores: np.ndarray, iou_thresh: float = 0.5):
    # boxes: [N, 4] -> [x1, y1, x2, y2]
    x1, y1, x2, y2 = boxes[:, 0], boxes[:, 1], boxes[:, 2], boxes[:, 3]
    areas = (x2 - x1) * (y2 - y1)
    
    # Sort scores descending
    order = scores.argsort()[::-1]
    keep = []

    while order.size > 0:
        i = order[0]
        keep.append(i)
        if order.size == 1:
            break
        
        # Compute IoU with remaining boxes
        xx1 = np.maximum(x1[i], x1[order[1:]])
        yy1 = np.maximum(y1[i], y1[order[1:]])
        xx2 = np.minimum(x2[i], x2[order[1:]])
        yy2 = np.minimum(y2[i], y2[order[1:]])

        w = np.maximum(0.0, xx2 - xx1)
        h = np.maximum(0.0, yy2 - yy1)
        inter = w * h
        ovr = inter / (areas[i] + areas[order[1:]] - inter)

        # Filter out overlapping boxes
        inds = np.where(ovr <= iou_thresh)[0]
        order = order[inds + 1] # Offset by 1 because of order[1:]

    return keep

# Test NMS
boxes = np.array([[10, 10, 50, 50], [12, 12, 48, 48], [100, 100, 200, 200]])
scores = np.array([0.9, 0.75, 0.85])
selected = nms_fast(boxes, scores, 0.5)
assert selected == [0, 2] # Box 1 suppressed!
```

**4. Interview Nuance / Real-World Pitfall:**
Off-by-one errors in `inds + 1` are a classic bug when updating `order`. Bounding box coordinates must be non-negative.

### Q66: How do you optimize column-wise sorting on massive matrices using transposition and contiguity re-establishment?
**1. Definition & Core Concept:**
Sorting columns (`axis=0`) on a C-contiguous matrix violates spatial cache locality. Transposing the matrix, enforcing C-contiguity, sorting along rows (`axis=1`), and transposing back eliminates cache misses.

**2. Technical & Memory Mechanics:**
For an $M \times N$ matrix:
- Direct column sort: Jumps $N \times \text{itemsize}$ bytes per element. Cache misses on every operation.
- Optimized route: `mat.T` creates a view with swapped strides ($O(1)$). `np.ascontiguousarray(mat.T)` copies data into row-major order ($O(MN)$ sequential memory write). `sort(axis=1)` executes at peak L1 cache speed. Final `.T` is $O(1)$.

**3. Explanatory Code Snippet:**
```python
import numpy as np
import time

mat = np.random.randn(3000, 3000)

# Benchmark 1: Direct Column Sort
t0 = time.perf_counter()
res1 = np.sort(mat, axis=0)
t_direct = time.perf_counter() - t0

# Benchmark 2: Transposition + Contiguity Route
t0 = time.perf_counter()
t_mat = np.ascontiguousarray(mat.T)
t_mat.sort(axis=1)
res2 = t_mat.T
t_optimized = time.perf_counter() - t0

print(f"Direct column sort:     {t_direct * 1000:.2f} ms")
print(f"Contiguous row sort .T: {t_optimized * 1000:.2f} ms")
assert np.allclose(res1, res2)
```

**4. Interview Nuance / Real-World Pitfall:**
This optimization pays off when $N$ (columns) is large. The cost of the one-time contiguous memory copy is vastly outweighed by the elimination of millions of cache miss pipeline stalls during sorting.

### Q68: What are the hardware SIMD vectorization limits when sorting non-contiguous views?
**1. Definition & Core Concept:**
NumPy 2.0 SIMD sort networks (Google Highway / AVX-512) require arrays to be aligned and C-contiguous. Non-contiguous strided views automatically disable SIMD vectorization.

**2. Technical & Memory Mechanics:**
AVX-512 sorting networks load 512 bits (8 `float64` elements) per clock cycle via contiguous vector load instructions (`_mm512_loadu_pd`). When sorting a strided view (e.g. `arr[::2]`), the memory addresses are non-contiguous. The SIMD engine cannot issue contiguous vector loads and falls back to scalar Introsort, dropping throughput by up to 8x.

**3. Explanatory Code Snippet:**
```python
import numpy as np
import time

big = np.random.randn(2_000_000)

# Contiguous slice
contig = big[:1_000_000].copy()

# Strided non-contiguous slice (same number of elements)
strided = big[::2].copy() # note: copy makes it contiguous; to keep strided:
strided_view = big[::2]

t0 = time.perf_counter()
contig.sort() # Uses AVX-512 / Highway SIMD
t_contig = time.perf_counter() - t0

t0 = time.perf_counter()
strided_view.sort() # Falls back to scalar sort!
t_strided = time.perf_counter() - t0

print(f"Contiguous SIMD sort: {t_contig * 1000:.2f} ms")
print(f"Strided scalar sort:  {t_strided * 1000:.2f} ms")
```

**4. Interview Nuance / Real-World Pitfall:**
Always copy non-contiguous slices to contiguous arrays before sorting if sorting throughput is critical.

### Q69: How does multi-threaded sorting in NumPy behave across different axes?
**1. Definition & Core Concept:**
For 1D arrays, NumPy's internal sort routines are single-threaded. For multidimensional arrays along an axis, NumPy releases the GIL, allowing multiple threads to sort independent slices concurrently.

**2. Technical & Memory Mechanics:**
When sorting an array of shape $(M, N)$ along `axis=1`, the operations on each of the $M$ rows are completely independent. While NumPy's built-in `np.sort` may execute sequentially depending on compilation flags, developers can dispatch slices across threads using `concurrent.futures.ThreadPoolExecutor` with zero lock contention because the GIL is released during array operations.

### Q70: How do you architect an out-of-core sorting pipeline for a 100 GB array on a 16 GB RAM workstation?
**1. Definition & Core Concept:**
When an array exceeds physical RAM, standard in-memory sorting triggers swapping and OOM crashes. An out-of-core sorting pipeline uses **External Merge Sort** combined with memory-mapped chunks (`np.memmap`).

**2. Technical & Memory Mechanics:**
1. **Chunk Sort Phase**:
   - Stream the 100 GB file in 2 GB chunks into RAM.
   - Sort each 2 GB chunk in-place using `np.sort()`.
   - Write each sorted chunk to a temporary scratch file on NVMe disk.
2. **K-Way Merge Phase**:
   - Open all 50 sorted chunk files as `np.memmap` views.
   - Use a min-heap of size 50 containing the smallest element from each chunk.
   - Repeatedly pop the global minimum from the heap and stream it to the final output file, replenishing the heap from the corresponding chunk view.
Memory footprint: strictly bounded below 4 GB RAM regardless of dataset size!

**3. Explanatory Code Snippet:**
```python
import numpy as np
import heapq
import tempfile

def external_merge_sort_demo():
    # Simulate external sorting with 3 small chunks
    chunk1 = np.array([10, 50, 90])
    chunk2 = np.array([20, 60, 80])
    chunk3 = np.array([15, 25, 75])
    
    chunks = [chunk1, chunk2, chunk3]
    heap = []
    
    # Initialize min-heap with (value, chunk_idx, element_idx)
    for c_idx, c in enumerate(chunks):
        heapq.heappush(heap, (c[0], c_idx, 0))
    
    sorted_output = []
    while heap:
        val, c_idx, e_idx = heapq.heappop(heap)
        sorted_output.append(val)
        if e_idx + 1 < len(chunks[c_idx]):
            next_val = chunks[c_idx][e_idx + 1]
            heapq.heappush(heap, (next_val, c_idx, e_idx + 1))
            
    print("External sorted output:", sorted_output)
    assert sorted_output == [10, 15, 20, 25, 50, 60, 75, 80, 90]

external_merge_sort_demo()
```

**4. Interview Nuance / Real-World Pitfall:**
In production external sorts, use asynchronous double-buffering for disk I/O so disk reads overlap with heap processing.

## 4. What If Scenarios

### Scenario 1: What if you call `arr.sort()` on an array that has `flags.writeable = False`?
**Outcome**: NumPy immediately raises a `ValueError: assignment destination is read-only`.
**Mechanics**: In-place sorting mutates bytes directly at `arr->data`. If the writeable bit is cleared, NumPy enforces write protection to prevent corrupting read-only views, memory-mapped shared files, or constant buffers.
```python
import numpy as np
arr = np.array([3, 1, 2])
arr.flags.writeable = False
try:
    arr.sort()
except ValueError as e:
    print("Caught expected writeable violation:", e)
```

### Scenario 2: What if you sort an array containing both `+inf`, `-inf`, finite numbers, and multiple `NaN` values?
**Outcome**: `-inf` is sorted to the very beginning, followed by finite numbers in ascending order, followed by `+inf`, followed by all `NaN` values at the very end.
**Mechanics**: NumPy's IEEE 754 sorting comparator orders `-inf < finite < +inf < nan`.
```python
import numpy as np
arr = np.array([np.nan, 5.0, -np.inf, np.nan, np.inf, -10.0])
res = np.sort(arr)
assert np.isneginf(res[0])
assert res[1] == -10.0
assert res[2] == 5.0
assert np.isposinf(res[3])
assert np.isnan(res[4]) and np.isnan(res[5])
```

### Scenario 3: What if you run `arr.sort(axis=0)` on a 2D matrix representing tabular records?
**Outcome**: Data corruption! Each column is sorted independently, breaking all row-wise associations between attributes.
**Mechanics**: Axis sorting operates on 1D slices in isolation. Column 0 is sorted; Column 1 is sorted; elements never cross column boundaries.
```python
import numpy as np
records = np.array([[101, 50], [102, 10]])
records.sort(axis=0) # Scrambles IDs and values!
assert records[0, 0] == 101 and records[0, 1] == 10 # ID 101 now associated with 10!
```

### Scenario 4: What if you pass keys in forward order `(primary, secondary)` to `np.lexsort()`?
**Outcome**: The array is sorted primarily by `secondary` and secondarily by `primary` (the exact opposite of your intent)!
**Mechanics**: `lexsort` uses right-to-left priority: the last argument is the primary key.
```python
import numpy as np
pri = np.array([2, 1, 2, 1])
sec = np.array([90, 50, 10, 80])
# WRONG:
idx_wrong = np.lexsort((pri, sec)) # Sorts primarily by sec!
# CORRECT:
idx_correct = np.lexsort((sec, pri)) # Sorts primarily by pri!
assert pri[idx_correct[0]] == 1 and sec[idx_correct[0]] == 50
```

### Scenario 5: What if you sort an array with duplicate keys using `kind='quicksort'` versus `kind='stable'`?
**Outcome**: In `kind='quicksort'`, the relative order of duplicate items may be permuted non-deterministically. In `kind='stable'`, duplicate items strictly maintain their original relative input order.
**Mechanics**: Introsort's partitioning algorithm swaps items across the pivot without checking initial index positions. Timsort (`stable`) preserves run order during merge operations.
```python
import numpy as np
keys = np.array([10, 20, 10, 20])
idx_stable = np.argsort(keys, kind='stable')
assert np.array_equal(idx_stable, [0, 2, 1, 3])
```

### Scenario 6: What if you use `np.partition(arr, 5)` and inspect the elements before index 5?
**Outcome**: All elements at indices `0..4` are guaranteed to be less than or equal to `arr[5]`, but they are **not in sorted order**.
**Mechanics**: Introselect partitions the array into two subsets without sorting within the subsets.
```python
import numpy as np
data = np.array([50, 10, 40, 20, 30, 80, 70])
part = np.partition(data, 3)
assert part[3] == 30 # Exactly the 4th smallest element
assert set(part[:3]) == {10, 20, 30} or all(x <= part[3] for x in part[:3])
```

### Scenario 7: What if you sort a complex number array: does it sort by magnitude?
**Outcome**: No! It sorts lexicographically by real part first, then by imaginary part.
**Mechanics**: Complex sorting checks `real < other.real`, breaking ties with `imag < other.imag`.
```python
import numpy as np
c = np.array([1 + 10j, 2 + 1j])
res = np.sort(c)
# 1+10j has magnitude ~10.05; 2+1j has magnitude ~2.23.
# Yet 1+10j comes FIRST because real part 1 < 2!
assert res[0] == 1 + 10j
```

### Scenario 8: What if you sort an array of strings containing uppercase and lowercase characters?
**Outcome**: All uppercase words sort before all lowercase words (ASCII order: `'Zebra' < 'apple'`).
**Mechanics**: NumPy string sorting compares Unicode code points or ASCII byte values.
```python
import numpy as np
words = np.array(['banana', 'Apple'])
assert np.sort(words)[0] == 'Apple'
```

### Scenario 9: What if you call `np.searchsorted()` on an unsorted array?
**Outcome**: It returns nonsensical index values without raising any error or warning!
**Mechanics**: Binary search relies on the invariant that the array is monotonically non-decreasing. If the invariant is violated, the algorithm branches unpredictably.
```python
import numpy as np
unsorted = np.array([50, 10, 40, 20])
idx = np.searchsorted(unsorted, 25)
# idx is invalid and cannot be trusted!
```

### Scenario 10: What if you slice an array with negative strides (`arr[::-1]`) and pass it to `np.sort()`?
**Outcome**: `np.sort(arr[::-1])` returns a new contiguous array sorted in ascending order.
**Mechanics**: Functional `np.sort()` copies the elements into a fresh buffer and sorts them ascending.
```python
import numpy as np
arr = np.array([1, 4, 2, 5])
assert np.array_equal(np.sort(arr[::-1]), [1, 2, 4, 5])
```

### Scenario 11: What if you sort an array with `kth` containing negative integers in `np.partition(arr, kth)`?
**Outcome**: Negative integers index from the end: `kth = -1` places the maximum element at the last position; `kth = -K` partitions the top-$K$ largest elements into the last $K$ positions.
**Mechanics**: Python negative index wrapping applies: `kth = len(arr) + kth`.
```python
import numpy as np
data = np.array([10, 90, 20, 80, 30])
part = np.partition(data, -2) # 2 largest elements at the end
assert set(part[-2:]) == {80, 90}
```

### Scenario 12: What if you execute `arr.sort()` on a multi-dimensional transposed view `mat.T`?
**Outcome**: It sorts along the last axis of `mat.T` in-place, modifying the underlying `mat` buffer!
**Mechanics**: The transposed view shares memory with `mat`. Sorting `mat.T` along its last axis mutates the bytes along that strided dimension.
```python
import numpy as np
mat = np.array([[9, 2], [5, 1]])
mat.T.sort(axis=-1)
assert mat.flags.owndata
```

### Scenario 13: What if you execute double `argsort()` on an array: `np.argsort(np.argsort(arr))`?
**Outcome**: It computes the **ranks** (ordinal positions) of the original elements!
**Mechanics**: The first `argsort` computes indices that order the values. The second `argsort` computes where each original element ends up in the sorted array.
```python
import numpy as np
arr = np.array([50, 10, 30, 20])
ranks = np.argsort(np.argsort(arr))
print("Ranks:", ranks) # [3, 0, 2, 1]
assert ranks[1] == 0 # 10 is the smallest (rank 0)
assert ranks[0] == 3 # 50 is the largest (rank 3)
```

## 5. Subtle Mistakes & Anti-Patterns

### Anti-Pattern 1: The Disappearing Array (`arr = arr.sort()`)
**Mistake**: Reassigning an array to the return value of its in-place sort method.
**Consequence**: `arr` becomes `None`.
**Correction**: Call `arr.sort()` without assignment, or use `arr = np.sort(arr)`.

### Anti-Pattern 2: The Independent Column Sort Scramble
**Mistake**: Calling `table.sort(axis=0)` on a 2D table expecting rows to remain intact.
**Consequence**: Column values are sorted independently, destroying row record integrity.
**Correction**: Use `table[table[:, col_idx].argsort()]`.

### Anti-Pattern 3: The Descending NaN Flip Trap
**Mistake**: Sorting descending using `np.sort(arr)[::-1]` when `NaN` values are present.
**Consequence**: `NaN` values are flipped to index 0, corrupting subsequent numerical calculations.
**Correction**: Filter out `NaN` values before sorting, or mask and append `NaN`s to the end.

### Anti-Pattern 4: The Unsigned Negation Underflow Trap
**Mistake**: Sorting descending by negating unsigned integers: `-np.sort(-u_arr)`.
**Consequence**: Modular underflow scrambles data completely.
**Correction**: Always use `np.sort(u_arr)[::-1]`.

### Anti-Pattern 5: The Inverted Lexsort Priority Tuple
**Mistake**: Passing keys to `np.lexsort()` in standard forward order `(primary, secondary)`.
**Consequence**: Data is sorted by secondary key first, producing inverted sorting.
**Correction**: Always pass keys in reverse order: `np.lexsort((secondary, primary))`.

### Anti-Pattern 6: Calling Full Sort for Top-$K$ Filtering
**Mistake**: Running `np.sort(arr)[-K:]` or `np.argsort(arr)[-K:]` on a massive array.
**Consequence**: Burns $O(N \log N)$ compute when $O(N)$ is achievable.
**Correction**: Use `np.partition(arr, -K)[-K:]` or `np.argpartition(arr, -K)[-K:]`.

### Anti-Pattern 7: Calling `np.searchsorted()` on Unsorted Data
**Mistake**: Querying insertion indices on an unsorted array without sorting first.
**Consequence**: Returns garbage indices without error.
**Correction**: Guarantee that the haystack array is sorted before calling `searchsorted`.

### Anti-Pattern 8: Converting Structured Arrays Unnecessarily
**Mistake**: Converting a 2D float matrix to a structured array just to sort by multiple columns.
**Consequence**: Incurs expensive memory allocation and data copying.
**Correction**: Use `np.lexsort(matrix.T[::-1])`.

### Anti-Pattern 9: The Masked In-Place Sort Failure
**Mistake**: Writing `arr[mask].sort()` expecting to sort elements in-place inside `arr`.
**Consequence**: `arr[mask]` returns a copy; the sort mutates that temporary copy and discards it.
**Correction**: Use `arr[mask] = np.sort(arr[mask])`.

### Anti-Pattern 10: Using Python `sorted(arr)` on NumPy Arrays
**Mistake**: Passing a NumPy array to built-in `sorted(arr)`.
**Consequence**: Converts array to a Python list of NumPy scalar objects, wasting memory and executing 10x slower.
**Correction**: Always use `np.sort(arr)` or `arr.sort()`.

## 6. What Confusion / Trap

### Trap 1: `np.sort()` vs `ndarray.sort()`
**Confusion**: Developers expect `np.sort(a)` to sort in-place or `a.sort()` to return a sorted array.
**Reality**: `np.sort(a)` returns a sorted copy. `a.sort()` mutates in-place and returns `None`.

### Trap 2: `lexsort` Argument Order
**Confusion**: Developers assume `lexsort((A, B))` sorts by $A$, then $B$.
**Reality**: `lexsort((A, B))` sorts primarily by $B$, and secondarily by $A$.

### Trap 3: Multidimensional `argsort` Indexing
**Confusion**: Developers assume `mat[np.argsort(mat, axis=1)]` sorts each row.
**Reality**: It triggers multidimensional broadcast indexing. You must use `np.take_along_axis(mat, np.argsort(mat, axis=1), axis=1)`.

### Trap 4: Complex Number Sorting Criteria
**Confusion**: Developers assume complex numbers sort by magnitude $\sqrt{x^2 + y^2}$.
**Reality**: NumPy sorts complex numbers lexicographically by real part first, then imaginary part.

### Trap 5: `searchsorted` Insertion vs Existence
**Confusion**: Developers assume `searchsorted` checks if an element exists in the array.
**Reality**: `searchsorted` returns the *insertion index* where the element belongs. The element at that index may or may not equal the search key.

## 7. Deep Traps & Edge Cases

### Deep Trap 1: In-Place Sort on Views of Shared Memory Mutating External Processes
If a NumPy array wraps POSIX shared memory (`multiprocessing.shared_memory`), calling `.sort()` in-place modifies the memory visible to all other OS worker processes without locking, creating race conditions.

### Deep Trap 2: Slicing Non-Unit Strides Disabling SIMD Bitonic Sorting
Slicing an array with step $> 1$ (e.g. `arr[::2]`) forces scalar fallback in Introsort because SIMD sorting kernels require contiguous memory addresses.

### Deep Trap 3: Timsort Merge Buffer Memory Spikes on Constrained Containers
`kind='stable'` allocates up to $0.5 \times \text{array size}$ in auxiliary merge buffers, which can trigger the Linux OOM killer on Docker containers with strict memory limits.

### Deep Trap 4: Loss of Record Association During Axis-0 Sorts
Sorting a 2D matrix along `axis=0` sorts each column independently, destroying all row-level correlations.

### Deep Trap 5: String Collation Failure on International Unicode Text
NumPy sorts Unicode strings by raw code point numerical values, failing linguistic collation rules (e.g., uppercase before lowercase, unaccented before accented).

### Deep Trap 6: Undefined NaN Ordering in Custom Structured Comparisons
If a structured array has multiple float fields containing `NaN`s, sorting with `order` can produce inconsistent record orderings if field comparisons do not handle `NaN` explicitly.

### Deep Trap 7: Unstable Sort Reproducibility Breakages Across NumPy Minor Versions
Algorithm updates in Introsort pivot selection between NumPy versions can change the order of equal keys in `kind='quicksort'`, breaking regression tests.

### Deep Trap 8: Binary Search Failures with Inf Values in `searchsorted`
If an array contains `+inf` or `-inf`, passing `inf` to `searchsorted` requires understanding whether `side='left'` or `side='right'` was chosen, especially when multiple infinite values exist.

### Deep Trap 9: Unaligned Struct Field Sorting Triggering Hardware Bus Errors
On strict RISC architectures (SPARC, ARM), sorting structured arrays with unaligned fields can cause hardware `SIGBUS` alignment exceptions.

### Deep Trap 10: Double Argsort Performance Overhead on Massive Vectors
While double `argsort` computes ranks cleanly, it allocates two full `intp` index vectors ($16 \times N$ bytes). For massive arrays, memory-efficient ranking algorithms are preferred.

### Q71: How do you architect a high-throughput streaming quantile estimator using reservoir sampling and in-place `partition()`?
**1. Definition & Core Concept:**
In streaming telemetry systems receiving millions of events per second, computing exact percentiles (e.g. p50, p95, p99) by sorting all events causes memory explosion. A fixed-capacity reservoir buffer paired with `np.partition()` computes exact windowed quantiles in $O(W)$ time without memory allocation.

**2. Technical & Memory Mechanics:**
- Pre-allocate a static reservoir array of size $W$ (e.g. $W=100,000$).
- When computing the $q$-th percentile, determine index $k = \lfloor q \times (W - 1) \rfloor$.
- Call `scratchpad.partition(k)` in-place on a temporary view or scratch buffer.
- The element at `scratchpad[k]` is the exact $q$-th quantile. Time complexity: $O(W)$ linear time; auxiliary memory: $O(1)$ bytes.

**3. Explanatory Code Snippet:**
```python
import numpy as np

class StreamingQuantileEstimator:
    def __init__(self, window_size: int = 1000):
        self.window_size = window_size
        self.buffer = np.zeros(window_size, dtype=np.float64)
        self.scratch = np.zeros(window_size, dtype=np.float64)
        self.count = 0

    def add_batch(self, batch: np.ndarray):
        n = len(batch)
        if n >= self.window_size:
            self.buffer[:] = batch[-self.window_size:]
        else:
            self.buffer[:-n] = self.buffer[n:]
            self.buffer[-n:] = batch
        self.count = min(self.count + n, self.window_size)

    def compute_percentile(self, q: float) -> float:
        assert 0.0 <= q <= 1.0 and self.count > 0
        active = self.buffer[-self.count:]
        k = int(q * (len(active) - 1))
        
        # Copy to scratchpad and partition in O(N)
        np.copyto(self.scratch[:len(active)], active)
        work = self.scratch[:len(active)]
        work.partition(k)
        return work[k]

estimator = StreamingQuantileEstimator(window_size=100)
estimator.add_batch(np.arange(1, 101, dtype=np.float64))
p50 = estimator.compute_percentile(0.50)
p95 = estimator.compute_percentile(0.95)

print(f"p50: {p50}, p95: {p95}")
assert p50 == 50.0 or p50 == 51.0
assert p95 == 95.0 or p95 == 96.0
```

**4. Interview Nuance / Real-World Pitfall:**
Calling `np.percentile()` on the full streaming history re-sorts the entire array on every request ($O(N \log N)$). Using pre-allocated buffers with in-place `partition()` cuts latency from milliseconds to microseconds.

### Q72: How do you design a thread-safe order book matching engine using `searchsorted` and contiguous memory blocks?
**1. Definition & Core Concept:**
A matching engine processes limit orders and market orders. Maintaining a sorted price-level depth table using binary search insertion eliminates sort overhead and ensures sub-microsecond tick processing.

**2. Technical & Memory Mechanics:**
Pre-allocate bid and ask price/size matrices of shape `(MAX_DEPTH, 2)`. When an order is placed:
- Use `np.searchsorted()` on active prices to locate insertion rank in $O(\log N)$.
- Shift lower rows using `np.copyto` and write the new order.
- To execute a market buy order, match against `asks[0]`; if filled, shift the remaining asks up.

**3. Explanatory Code Snippet:**
```python
import numpy as np

class FastOrderBook:
    def __init__(self, capacity: int = 100):
        # Asks: sorted ascending by price
        self.asks_price = np.full(capacity, np.inf, dtype=np.float64)
        self.asks_size  = np.zeros(capacity, dtype=np.float64)
        self.ask_count = 0

    def add_limit_ask(self, price: float, size: float):
        # Binary search for insertion point
        idx = np.searchsorted(self.asks_price[:self.ask_count], price)
        
        # Shift down
        self.asks_price[idx+1:self.ask_count+1] = self.asks_price[idx:self.ask_count]
        self.asks_size[idx+1:self.ask_count+1] = self.asks_size[idx:self.ask_count]
        
        # Insert
        self.asks_price[idx] = price
        self.asks_size[idx] = size
        self.ask_count += 1

    def match_market_buy(self, order_size: float) -> float:
        # Fills against best ask (index 0)
        assert self.ask_count > 0
        best_price = self.asks_price[0]
        fill_size = min(order_size, self.asks_size[0])
        self.asks_size[0] -= fill_size
        
        if self.asks_size[0] == 0:
            # Shift remaining asks up
            self.asks_price[:self.ask_count-1] = self.asks_price[1:self.ask_count]
            self.asks_size[:self.ask_count-1] = self.asks_size[1:self.ask_count]
            self.asks_price[self.ask_count-1] = np.inf
            self.asks_size[self.ask_count-1] = 0.0
            self.ask_count -= 1
            
        return best_price * fill_size

book = FastOrderBook(10)
book.add_limit_ask(102.5, 10.0)
book.add_limit_ask(101.0, 5.0) # Best ask
book.add_limit_ask(105.0, 20.0)

cost = book.match_market_buy(5.0)
assert cost == 101.0 * 5.0
assert book.asks_price[0] == 102.5 # 102.5 is now best ask!
```

**4. Interview Nuance / Real-World Pitfall:**
In-place memory shifting with `self.asks_price[idx+1:] = ...` uses C `memmove` under the hood, executing in tens of nanoseconds for small depths ($D \le 100$), which is significantly faster than linked-list pointer hopping.

### Q73: In real-time computer vision inference, how do you accelerate batched Non-Maximum Suppression (NMS) across thousands of bounding boxes?
**1. Definition & Core Concept:**
Real-time object detectors (YOLO, Faster R-CNN) generate thousands of bounding boxes per frame across multiple object classes. Sorting boxes globally is slow. Batched NMS separates boxes by class ID and sorts scores in parallel.

**2. Technical & Memory Mechanics:**
To process boxes across classes in a single vectorized pass:
- Offset bounding box coordinates by class ID: `offset_boxes = boxes + class_ids[:, None] * 10000.0`.
- Sort all boxes descending by confidence score: `order = np.argsort(scores)[::-1]`.
- Because boxes of different classes are shifted by 10,000 pixels, their IoU across different classes evaluates to 0, allowing a single unified NMS loop to filter all classes simultaneously!

**3. Explanatory Code Snippet:**
```python
import numpy as np

def batched_nms(boxes: np.ndarray, scores: np.ndarray, class_ids: np.ndarray, iou_thresh: float = 0.5):
    # Offset coordinates by class to isolate classes
    max_coord = 10000.0
    offsets = class_ids[:, None] * max_coord
    shifted_boxes = boxes + offsets
    
    # Standard NMS on shifted boxes
    x1, y1, x2, y2 = shifted_boxes.T
    areas = (x2 - x1) * (y2 - y1)
    order = scores.argsort()[::-1]
    keep = []

    while order.size > 0:
        i = order[0]
        keep.append(i)
        if order.size == 1:
            break
        xx1 = np.maximum(x1[i], x1[order[1:]])
        yy1 = np.maximum(y1[i], y1[order[1:]])
        xx2 = np.minimum(x2[i], x2[order[1:]])
        yy2 = np.minimum(y2[i], y2[order[1:]])

        w = np.maximum(0.0, xx2 - xx1)
        h = np.maximum(0.0, yy2 - yy1)
        inter = w * h
        ovr = inter / (areas[i] + areas[order[1:]] - inter)

        inds = np.where(ovr <= iou_thresh)[0]
        order = order[inds + 1]

    return keep

# Test batched NMS: Two overlapping boxes of DIFFERENT classes should BOTH be kept!
boxes = np.array([[10, 10, 50, 50], [10, 10, 50, 50]])
scores = np.array([0.9, 0.85])
classes = np.array([0, 1]) # Class 0 (person), Class 1 (backpack)

assert len(kept) == 2 # Both preserved because classes differ!
```

**4. Interview Nuance / Real-World Pitfall:**
The coordinate offset trick (`boxes + class_ids * max_coord`) is the exact implementation used in TorchVision and TensorRT to run multi-class NMS in a single GPU/CPU kernel without Python class-filtering loops.

### Q74: How do you design an out-of-core External Merge Sort for a 50 GB financial tick dataset using `np.memmap`?
**1. Definition & Core Concept:**
When sorting a 50 GB array on a machine with 8 GB of RAM, in-memory sorting triggers swapping and crashes. External Merge Sort breaks the array into memory-sized chunks, sorts each chunk into temporary files, and merges them using a priority queue.

**2. Technical & Memory Mechanics:**
1. Chunk Phase: Stream the 50 GB file in 1 GB blocks. Sort each 1 GB block in-place using `np.sort()` and save to disk.
2. Merge Phase: Open all 50 sorted chunk files as `np.memmap` views. Maintain a min-heap of 50 elements `(value, chunk_id, index)`. Pop minimum, write to output, and push the next element from that chunk.

**3. Explanatory Code Snippet:**
```python
import numpy as np
import heapq
import tempfile

def external_sort_simulated():
    # Simulate with 3 on-disk sorted runs
    run1 = np.array([10, 40, 70], dtype=np.int64)
    run2 = np.array([20, 50, 80], dtype=np.int64)
    run3 = np.array([30, 60, 90], dtype=np.int64)
    runs = [run1, run2, run3]
    
    # Priority queue min-heap
    heap = []
    for r_idx, r in enumerate(runs):
        heapq.heappush(heap, (r[0], r_idx, 0))
        
    out = []
    while heap:
        val, r_idx, elem_idx = heapq.heappop(heap)
        out.append(val)
        if elem_idx + 1 < len(runs[r_idx]):
            next_val = runs[r_idx][elem_idx + 1]
            heapq.heappush(heap, (next_val, r_idx, elem_idx + 1))
            
    print("External merge sort result:", out)
    assert out == [10, 20, 30, 40, 50, 60, 70, 80, 90]

external_sort_simulated()
```

**4. Interview Nuance / Real-World Pitfall:**
In production external sorts, memory-mapped views must be read sequentially with OS read-ahead flags (`posix_madvise(MADV_SEQUENTIAL)`) to prevent random NVMe disk thrashing.

## 11. Debugging Scenarios

### Scenario 1: The Vanishing Array (`arr = arr.sort()`)
**The Symptom**: A developer writes a data pre-processing function. After calling the function, downstream code crashes with `AttributeError: 'NoneType' object has no attribute 'shape'`.
**The Investigation**: Looking at the source code reveals:
```python
def preprocess(data):
    data = data.sort() # Returns None!
    return data
```
`ndarray.sort()` mutates the array in-place and returns `None`. Reassigning `data = data.sort()` destroys the array reference!
**The Fix**:
```python
def preprocess(data):
    data.sort() # Mutate in-place
    return data # or return np.sort(data)
```

### Scenario 2: The Silent NaN Displacement Disaster
**The Symptom**: An algorithmic trading backtest that buys the top 5 stocks by return suddenly begins purchasing stocks that traded zero volume or went bankrupt.
**The Investigation**: The engineer wrote:
```python
top_stocks = stock_returns.argsort()[::-1][:5]
```
When `stock_returns` contains `NaN` values (for untraded or delisted stocks), NumPy sorts `NaN` to the end in ascending order. When reversed with `[::-1]`, all the `NaN` values move to the **front** (indices 0..4)! The backtest was buying the 5 `NaN` stocks!
**The Fix**: Filter out `NaN` values before indexing, or use `np.nan_to_num(returns, nan=-np.inf)` before sorting descending.

### Scenario 3: The Scrambled Database Table (`table.sort(axis=0)`)
**The Symptom**: In a user demographic dataset of `[User_ID, Age, Income]`, a data analyst called `table.sort(axis=0)`. Afterwards, young users have high incomes and IDs no longer match user profiles.
**The Investigation**: `table.sort(axis=0)` sorted each column independently! User IDs were sorted 1..N; Ages were sorted 18..99; Incomes were sorted 10k..500k. The horizontal relationship between attributes across each row was permanently destroyed.
**The Fix**: Reorder rows using `argsort` on the key column:
```python
table = table[table[:, 1].argsort()] # Sort rows by Age intact!
```

## 13. Flashcard Study Deck

- **Flashcard 1**:
  - *Front*: What is the difference between `np.sort(a)` and `a.sort()`?
  - *Back*: `np.sort(a)` returns a sorted copy ($O(N)$ memory). `a.sort()` mutates the buffer in-place and returns `None` ($O(1)$ memory).

- **Flashcard 2**:
  - *Front*: What sorting algorithm is implemented by `kind='quicksort'` in NumPy?
  - *Back*: **Introsort** (hybrid of QuickSort, HeapSort, and InsertionSort). It guarantees $O(N \log N)$ worst-case time by falling back to HeapSort if recursion depth exceeds $2 \log_2(N)$.

- **Flashcard 3**:
  - *Front*: Why does `lexsort((k2, k1))` take keys in reverse order?
  - *Back*: It follows dictionary ordering conventions where the primary key is evaluated last: `k1` is primary, `k2` is secondary.

- **Flashcard 4**:
  - *Front*: What is the computational complexity of `np.partition(arr, k)` vs `np.sort(arr)`?
  - *Back*: `np.partition` runs in $O(N)$ linear time (Introselect). `np.sort` runs in $O(N \log N)$ time.

- **Flashcard 5**:
  - *Front*: How do you sort an entire 2D table by Column $C$ without scrambling row records?
  - *Back*: `table[table[:, C].argsort()]`.

- **Flashcard 6**:
  - *Front*: How does `np.searchsorted(arr, val, side='left')` differ from `side='right'` on duplicates?
  - *Back*: `side='left'` returns the index of the first occurrence; `side='right'` returns the index after the last occurrence.

- **Flashcard 7**:
  - *Front*: What happens to `NaN`s when sorting descending using `np.sort(arr)[::-1]`?
  - *Back*: Because `NaN`s sort to the end ascending, reversing flips `NaN`s to the very beginning (index 0).

- **Flashcard 8**:
  - *Front*: What does double `argsort` (`np.argsort(np.argsort(arr))`) produce?
  - *Back*: The 0-based numerical ranks (positions) of each element in the original array.

- **Flashcard 9**:
  - *Front*: What is the auxiliary memory consumption of `kind='stable'`?
  - *Back*: Up to $O(N/2)$ auxiliary heap memory for merge buffers.

- **Flashcard 10**:
  - *Front*: How does `np.take_along_axis(arr, idx, axis)` work?
  - *Back*: It indexes multi-dimensional arrays along `axis` using index matrices generated by `np.argsort()`.

- **Flashcard 11**:
  - *Front*: Why does `arr = arr.sort()` destroy your array?
  - *Back*: `arr.sort()` returns `None`. Reassigning sets `arr = None`.

- **Flashcard 12**:
  - *Front*: How do complex numbers sort in NumPy?
  - *Back*: Real part first; if real parts are equal, by imaginary part. Not by magnitude.

- **Flashcard 13**:
  - *Front*: When is Timsort (`kind='stable'`) faster than QuickSort?
  - *Back*: When data is already partially or completely pre-sorted (runs in $O(N)$ time).

- **Flashcard 14**:
  - *Front*: Why does `-np.sort(-uint_arr)` fail for descending sorts on unsigned integers?
  - *Back*: Negating unsigned integers triggers modular underflow wrapping (e.g. `-1` becomes `255` in `uint8`).

- **Flashcard 15**:
  - *Front*: How do you sort a structured array by multiple named fields?
  - *Back*: `arr.sort(order=['field1', 'field2'])`.

## 15. Real-World Design Patterns

### Pattern 1: The Top-$K$ Linear-Time Extraction Pattern
Extract the top $K$ largest elements and sort only the top $K$ subset in $O(N + K \log K)$ time.
```python
import numpy as np

def extract_top_k(arr: np.ndarray, K: int) -> tuple[np.ndarray, np.ndarray]:
    cand = np.argpartition(arr, -K)[-K:]
    sub_order = cand[np.argsort(arr[cand])[::-1]]
    return arr[sub_order], sub_order
```

### Pattern 2: The Whole-Row Table Sorter Pattern
Sort entire records in a 2D matrix based on a key column while preserving row integrity.
```python
import numpy as np

def sort_table_by_col(table: np.ndarray, col_idx: int, ascending: bool = True) -> np.ndarray:
    order = np.argsort(table[:, col_idx])
    if not ascending:
        order = order[::-1]
    return table[order]
```

### Pattern 3: The NaN-Safe Descending Sorter Pattern
Safely sort arrays containing missing `NaN` values descending without pushing `NaN`s to index 0.
```python
import numpy as np

def nan_safe_sort_desc(arr: np.ndarray) -> np.ndarray:
    nan_mask = np.isnan(arr)
    valid = np.sort(arr[~nan_mask])[::-1]
    res = np.empty_like(arr)
    res[:len(valid)] = valid
    res[len(valid):] = np.nan
    return res
```

### Pattern 4: Contiguity-Optimized Column Sorter Pattern
Transpose, ensure C-contiguity for SIMD, sort along rows, and transpose back for maximum speed.
```python
import numpy as np

def fast_col_sort(mat: np.ndarray) -> np.ndarray:
    c_trans = np.ascontiguousarray(mat.T)
    c_trans.sort(axis=1)
    return c_trans.T
```

## 17. Architecture & System Design Style Interview Questions

### Q76: How would you architect a real-time order matching engine processing 100,000 orders/sec using NumPy?
**1. Definition & Core Concept:**
A high-frequency exchange order book maintains sorted price levels for bids and asks. The matching engine must match incoming market orders against the top price levels and insert limit orders in sub-microsecond latency without heap allocation.

**2. Technical & Memory Mechanics:**
- Maintain pre-allocated static 2D arrays `bids = np.zeros((CAPACITY, 2))` and `asks = np.zeros((CAPACITY, 2))` in POSIX shared memory.
- Bids are maintained descending; Asks are maintained ascending.
- When an order arrives, use `np.searchsorted()` on active prices to determine the insertion slot in $O(\log N)$ time.
- Shift lower rows using `np.copyto` and write the order.
- To execute market orders, fill against index 0 (`bids[0]` or `asks[0]`) in $O(1)$ time. Total latency: $< 500$ nanoseconds.

**3. Explanatory Code Snippet:**
```python
import numpy as np

class EngineL2Book:
    def __init__(self, depth: int = 100):
        self.bids = np.zeros((depth, 2), dtype=np.float64) # [Price, Size]
        self.count = 0

    def insert_bid(self, price: float, size: float):
        # Invert prices for binary search on descending bids
        active = -self.bids[:self.count, 0]
        slot = np.searchsorted(active, -price)
        
        # In-place C-level memory shift
        self.bids[slot+1:self.count+1] = self.bids[slot:self.count]
        self.bids[slot] = [price, size]
        self.count = min(self.count + 1, len(self.bids))

engine = EngineL2Book(10)
engine.insert_bid(100.5, 10)
engine.insert_bid(102.0, 50)
assert engine.bids[0, 0] == 102.0 # Best bid
```

**4. Interview Nuance / Real-World Pitfall:**
Avoid full array sorts on tick arrival! A full sort takes $O(N \log N)$; binary search insertion into pre-sorted arrays takes $O(\log N + \text{shift})$.

### Q77: How would you design a distributed Top-$K$ metric aggregator for a monitoring system processing 10 million metrics per second across 100 worker nodes?
**1. Definition & Core Concept:**
Each worker node monitors 100,000 metrics per second. The centralized aggregator must display the top 100 most anomalous latency spikes across all nodes with sub-second latency.

**2. Technical & Memory Mechanics:**
1. **Local Worker Reduction**:
   - Each worker uses `np.argpartition(latencies, -100)[-100:]` to extract its local top 100 candidates in $O(N)$ linear time.
   - Workers transmit only 100 metrics to the central coordinator (100 workers $\times$ 100 = 10,000 total candidates), eliminating network saturation.
2. **Global Coordinator Merge**:
   - The coordinator receives 10,000 candidates and runs `np.argpartition(candidates, -100)[-100:]`, followed by a final $O(K \log K)$ sort.

**3. Explanatory Code Snippet:**
```python
import numpy as np

def worker_local_top_k(latencies: np.ndarray, K: int = 100) -> np.ndarray:
    # O(N) local candidate extraction
    cand_idx = np.argpartition(latencies, -K)[-K:]
    return latencies[cand_idx]

def coordinator_global_merge(worker_batches: list[np.ndarray], K: int = 100) -> np.ndarray:
    all_candidates = np.concatenate(worker_batches)
    top_k_idx = np.argpartition(all_candidates, -K)[-K:]
    sorted_top_k = all_candidates[top_k_idx]
    sorted_top_k.sort()
    return sorted_top_k[::-1] # Descending

# Simulate 5 workers
w_data = [np.random.uniform(0, 1000, 50_000) for _ in range(5)]
w_tops = [worker_local_top_k(w, 10) for w in w_data]
global_top = coordinator_global_merge(w_tops, 10)
assert len(global_top) == 10
assert global_top[0] >= global_top[1]
```

**4. Interview Nuance / Real-World Pitfall:**
Transmitting raw metric streams across the network causes massive bandwidth saturation. Filtering via local `argpartition` beforehand is the cornerstone of distributed metric architectures (e.g. Prometheus, Datadog).

### Q78: In a video analytics pipeline processing 4K camera streams, how do you sort bounding box detections without stalling the GPU pipeline?
**1. Definition & Core Concept:**
A neural network produces 2,000 bounding box proposals per frame. Non-Maximum Suppression (NMS) requires sorting detection scores. Executing Python-level sorting stalls the video pipeline.

**2. Technical & Memory Mechanics:**
- Filter out boxes with confidence $< 0.1$ using boolean masking in $O(N)$ time, reducing candidates from 2,000 to ~50.
- Execute `scores.argsort()[::-1]` only on the surviving candidates.
- Run IoU suppression in a fast C/Cython loop.
- Processing latency drops from 15 ms to 0.4 ms per frame, sustaining 60 FPS 4K video streams.

**3. Explanatory Code Snippet:**
```python
import numpy as np

def fast_video_nms_pipeline(boxes: np.ndarray, scores: np.ndarray, conf_thresh: float = 0.5):
    # Step 1: Filter low confidence
    mask = scores >= conf_thresh
    if not np.any(mask):
        return []
    
    surviving_boxes = boxes[mask]
    surviving_scores = scores[mask]
    
    # Step 2: Sort only surviving candidates
    order = surviving_scores.argsort()[::-1]
    return surviving_boxes[order]

raw_boxes = np.random.uniform(0, 1000, (2000, 4))
raw_scores = np.random.uniform(0, 1, 2000)
filtered = fast_video_nms_pipeline(raw_boxes, raw_scores, 0.95)
print(f"Reduced 2000 boxes to {len(filtered)} candidates for NMS")
```

### Q79: How would you design a memory-efficient multi-key sorter for a 1-billion row database table in Python?
**1. Definition & Core Concept:**
A 1-billion row table of 3 integer columns consumes 24 GB of RAM. Running `np.lexsort()` requires allocating an 8 GB index array, which can exceed system RAM limits.

**2. Technical & Memory Mechanics:**
- Encode composite keys into a single 64-bit integer bitfield:
  $$\text{composite\_key} = (\text{col}_1 \ll 32) \mid \text{col}_2$$
- Sort the single 64-bit array using Radix Sort (`kind='stable'`), reducing sorting passes from multiple column sweeps to a single pass.
- Eliminates auxiliary index arrays and executes 4x faster.

**3. Explanatory Code Snippet:**
```python
import numpy as np

# Two 32-bit integer keys: Region (0..1000), User_ID (0..1000000)
regions  = np.array([2, 1, 2, 1], dtype=np.uint32)
user_ids = np.array([500, 100, 200, 400], dtype=np.uint32)

# Pack into single 64-bit key: (regions << 32) | user_ids
composite_keys = (regions.astype(np.uint64) << 32) | user_ids.astype(np.uint64)

# Single 1D sort
order = np.argsort(composite_keys, kind='stable')

print("Sorted Regions: ", regions[order])
print("Sorted User IDs:", user_ids[order])

assert regions[order[0]] == 1 and user_ids[order[0]] == 100
assert regions[order[1]] == 1 and user_ids[order[1]] == 400
assert regions[order[2]] == 2 and user_ids[order[2]] == 200
```

**4. Interview Nuance / Real-World Pitfall:**
Bit-packing composite keys into a single integer requires that the sum of field bit-widths fits within 64 bits (or 128 bits), but when applicable, it completely bypasses multi-key `lexsort` overhead.

### Q81: How do NumPy sorting algorithms correspond to C++ standard library sorting routines (`std::sort`, `std::stable_sort`, `std::nth_element`)?
**1. Definition & Core Concept:**
NumPy's sorting primitives directly mirror the C++ STL:
- `np.sort(..., kind='quicksort')` $\iff$ `std::sort` (Introsort)
- `np.sort(..., kind='stable')` $\iff$ `std::stable_sort` (Timsort / Mergesort)
- `np.partition(..., kth)` $\iff$ `std::nth_element` (Introselect)

**2. Technical & Memory Mechanics:**
Both NumPy and C++ STL use Introsort (QuickSort falling back to HeapSort) for unstable sorting and Introselect for linear-time partitioning. Both STL and NumPy use $O(N)$ auxiliary buffers for stable sorting.

**3. Explanatory Code Snippet:**

```cpp
// C++ STL Equivalent
// std::vector<double> v = {9.0, 2.0, 5.0, 1.0};

// std::stable_sort(v.begin(), v.end());          // np.sort(kind='stable')
// std::nth_element(v.begin(), v.begin()+2, v.end()); // np.partition(kth=2)
```

```python
# NumPy Equivalent
import numpy as np
v = np.array([9.0, 2.0, 5.0, 1.0])
s_quick = np.sort(v, kind='quicksort')
s_stable = np.sort(v, kind='stable')
p_part = np.partition(v, 2)
assert p_part[2] == 5.0
```

**4. Interview Nuance / Real-World Pitfall:**
C++ `std::nth_element` operates in-place. In NumPy, `arr.partition(kth)` operates in-place, while `np.partition(arr, kth)` returns a copy.

### Q82: How does Rust's slice sorting (`sort()` vs `sort_unstable()`) map to NumPy?
**1. Definition & Core Concept:**
In Rust:
- `slice.sort()` is **stable** by default (Timsort, allocating auxiliary memory).
- `slice.sort_unstable()` is **unstable** (Pattern-Defeating QuickSort, $O(1)$ memory).
In NumPy, the default is reversed: `np.sort()` is **unstable** by default!

**2. Technical & Memory Mechanics:**
Rust prioritizes safety and predictability by making stable sort the default `sort()`. NumPy prioritizes raw computational speed and memory conservation, defaulting to `kind='quicksort'` (unstable).

**3. Explanatory Code Snippet:**
```rust
// Rust:
// let mut v = vec![3, 1, 2];
// v.sort();          // Stable by default! (Allocates merge memory)
// v.sort_unstable(); // Unstable! O(1) memory
```
```python
# NumPy:
import numpy as np
v = np.array([3, 1, 2])
v.sort() # UNSTABLE by default!
# To get stable sort:
v.sort(kind='stable')
```

**4. Interview Nuance / Real-World Pitfall:**
Python developers moving to Rust are surprised that `v.sort()` allocates memory; Rust developers moving to Python are surprised that `np.sort()` is unstable by default.

### Q83: How do PyTorch tensor sorting functions (`torch.sort`, `torch.topk`) compare to NumPy?
**1. Definition & Core Concept:**
PyTorch's `torch.sort(input, dim=-1)` returns **both** the sorted values AND the sorting indices as a tuple `(values, indices)`. In NumPy, `np.sort()` returns only values; `np.argsort()` returns only indices.

**2. Technical & Memory Mechanics:**
On GPU hardware (CUDA), sorting values and indices simultaneously is executed via GPU Radix Sort (e.g. CUB / Thrust). In NumPy, computing both values and indices requires calling `idx = np.argsort(a)` followed by `values = a[idx]`.

**3. Explanatory Code Snippet:**
```python
import numpy as np

arr = np.array([40, 10, 30, 20])

# NumPy requires two steps:
idx = np.argsort(arr)
vals = arr[idx]

# PyTorch Equivalent:
# vals, idx = torch.sort(tensor, dim=-1)

assert np.array_equal(vals, [10, 20, 30, 40])
assert np.array_equal(idx, [1, 3, 2, 0])
```

**4. Interview Nuance / Real-World Pitfall:**
PyTorch's `torch.topk()` combines `argpartition` and `argsort` into a single highly optimized GPU kernel. In NumPy, you replicate this via `cand = np.argpartition(arr, -K)[-K:]` followed by `cand[np.argsort(arr[cand])[::-1]]`.

### Q84: How does SQL `ORDER BY` with `NULLS LAST` compare to NumPy sorting mechanics?
**1. Definition & Core Concept:**
In SQL standard:
`SELECT * FROM table ORDER BY score DESC NULLS LAST;`
In NumPy, standard descending sort `np.sort(a)[::-1]` places `NaN`s **first** (`NULLS FIRST`), directly violating standard business SQL expectations!

**2. Technical & Memory Mechanics:**
To emulate SQL `NULLS LAST` descending in NumPy, developers partition or mask `NaN` values, sorting only valid values descending and appending `NaN`s at the end.

**3. Explanatory Code Snippet:**
```python
import numpy as np

scores = np.array([85.0, np.nan, 95.0, 70.0])

# Emulating SQL: ORDER BY score DESC NULLS LAST
mask = ~np.isnan(scores)
sorted_valid = np.sort(scores[mask])[::-1]
sql_order = np.empty_like(scores)
sql_order[:len(sorted_valid)] = sorted_valid
sql_order[len(sorted_valid):] = np.nan

print("SQL NULLS LAST result:", sql_order)
# [95.0, 85.0, 70.0, nan]
assert sql_order[0] == 95.0
assert np.isnan(sql_order[-1])
```

**4. Interview Nuance / Real-World Pitfall:**
When writing data preprocessing layers feeding SQL databases or BI dashboards, failing to handle `NaN`s in descending sorts causes discrepancies between Python pipelines and database queries.

### Q85: How does Julia's `sortperm` compare with NumPy's `argsort`?
**1. Definition & Core Concept:**
Julia's `sortperm(A)` is equivalent to NumPy's `np.argsort(A)`. However, Julia uses 1-based indexing, so the returned permutation indices are 1-based, while NumPy's indices are 0-based.

## 19. Historical Evolution & NumPy 2.0 Impact

### The Evolution of Sorting Engines in NumPy
- **NumPy 1.0 (2006)**: Introduced Introsort for `'quicksort'`, standard recursive MergeSort for `'mergesort'`, and HeapSort for `'heapsort'`.
- **NumPy 1.15 (2018)**: Introduced `np.take_along_axis()` and `np.put_along_axis()`, solving the multi-dimensional `argsort` indexing problem.
- **NumPy 1.19 (2020)**: Modernized Timsort implementation for `'stable'` sorting, delivering $O(N)$ linear-time performance on partially sorted numeric arrays.
- **NumPy 1.24 (2022)**: Introduced SIMD sorting networks (AVX-512 sorting) for 1D numeric arrays, providing up to 10x acceleration for 16-bit, 32-bit, and 64-bit integer/float datatypes.

### NumPy 2.0 Major Enhancements & Deprecations
Released in 2024, **NumPy 2.0** brought critical sorting modernizations:
1. **Removal of `np.msort`**: The legacy `np.msort(a)` function was officially **removed**. All code must use `np.sort(a, axis=0)`.
2. **Universal SIMD Highway Integration**: Vectorized sorting networks were unified under Google Highway intrinsics, extending SIMD sorting acceleration to ARM Neon (Apple Silicon, AWS Graviton) alongside x86 AVX-512.
3. **String Sorting Overhaul**: NumPy 2.0 introduced the new StringDType, allowing variable-length UTF-8 strings. Sorting variable-length strings no longer requires fixed-width UCS-4 memory padding, reducing string sorting memory footprint by up to 75%.
4. **Stable Sort Unification**: `kind='mergesort'` and `kind='stable'` are now officially aliased to the same underlying adaptive radix/timsort engine.

## 24. Final Revision Summary

### 1-Page Rapid Memory Checklist
1. **`np.sort(a)` = Copy**: Returns sorted array; leaves original untouched.
2. **`a.sort()` = In-Place**: Mutates buffer in-place; returns `None`. Never write `a = a.sort()`.
3. **`np.argsort(a)` = Index Permutation**: Returns `intp` indices that sort the array.
4. **`np.lexsort((sec, pri))`**: Multi-key indirect sort; right-to-left priority (last key is primary).
5. **`np.partition(a, kth)`**: $O(N)$ linear time partial sort. Use for Top-$K$ selection instead of $O(N \log N)$ sort.
6. **`np.searchsorted(sorted_a, val)`**: $O(\log N)$ binary search insertion index into pre-sorted array.
7. **`take_along_axis(a, idx, axis)`**: Multi-dimensional indexing tool for applying `argsort` results along an axis.
8. **Table Row Sorting**: To sort a 2D table by Column $C$, use `table[table[:, C].argsort()]`.
9. **Descending NaN Trap**: `np.sort(a)[::-1]` moves `NaN`s to the front! Mask `NaN`s to keep them at the end.
10. **SIMD & Contiguity**: Sorting along contiguous rows (`axis=1`) is much faster than strided columns (`axis=0`). Transpose and ensure C-contiguity for fast column sorting.
